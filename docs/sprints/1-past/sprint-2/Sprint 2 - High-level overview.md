## Sprint Goal:

**To transform LexiSynth from a well-architected prototype into a functional end-to-end application by replacing mocked data retrieval with a live search integration, ensuring real data flows through the entire BAML pipeline, and dynamically populating all core UI elements with this live data.**

**Sprint Duration:** (Suggest 2-3 weeks, depending on team size and complexity of chosen search API integration)

**Key Focus Areas:**

1.  Live Document Retrieval Integration.
2.  End-to-End Data Flow Validation and BAML Prompt Refinement.
3.  Dynamic UI Population with Real Data.
4.  Minor Cleanup and Organizational Improvements.

---

### Phase 1: Search API Integration (Replacing Mocked Document Retrieval)

**Goal:** Integrate a live search API (e.g., Exa Search, for which `exaSearchUtil.ts` exists) into the server-side orchestrator.

**Tasks:**

1.  **Task 1.1: Setup and Secure Search API Credentials**
    *   **Action:** Obtain necessary API keys for the chosen search provider (e.g., Exa).
    *   **Details:**
        *   If using Exa, ensure the `EXA_API_KEY` is correctly set up in development environment variables (e.g., `.env.local`, `.env.development.local`) and is accessible server-side by `exaSearchUtil.ts`.
        *   Verify that `dotenv.config()` in `exaSearchUtil.ts` (or a global setup) correctly loads these variables. Per `setupTests.ts`, `.env.test` is loaded for tests, ensure a similar mechanism works for development/production.
    *   **Acceptance Criteria:**
        *   ✅ API key is securely stored and accessible by the server-side utility.
        *   ✅ `exaSearchUtil.ts` can successfully authenticate with the search API in a standalone test/script (if feasible outside the main app flow initially).
    *   **PRD Alignment:** NFR4.1 (Security - API keys).

2.  **Task 1.2: Integrate `executeExaSearch` into `researchAgentOrchestrator.ts`**
    *   **Action:** Replace the `fetchDocumentsFromQueries` mock function in `app/actions/researchAgentOrchestrator.ts` with calls to the actual `executeExaSearch` utility from `lib/utils/exaSearchUtil.ts`.
    *   **Details:**
        *   Import `executeExaSearch`.
        *   Modify the `fetchDocumentsFromQueries` (or integrate directly) to iterate over the `SearchQueryItem[]` generated by `b.GenerateLegalSearchQueries`.
        *   For each `SearchQueryItem`, call `executeExaSearch`.
        *   Consider how many `SearchQueryItem`s to process from the BAML output (e.g., top 3-5 queries) and how many results to fetch per query (e.g., `numResults` for `executeExaSearch`). This might require some configuration or heuristics.
        *   Aggregate results from multiple query executions. Handle potential duplicate documents if queries overlap.
        *   Map the `BamlSearchResultItem[]` returned by `executeExaSearch` to the `SearchResultItem[]` type expected by the rest of the orchestrator (they should be compatible if types are aligned).
    *   **Acceptance Criteria:**
        *   ✅ `fetchDocumentsFromQueries` (or its inline replacement) successfully calls `executeExaSearch` for generated queries.
        *   ✅ Results from the search API are correctly transformed/mapped to the BAML `SearchResultItem` type if necessary (though `exaSearchUtil` already aims to do this).
        *   ✅ The orchestrator proceeds with the actual list of `SearchResultItem` objects.
    *   **PRD Alignment:** FR2.3.1 (Pipeline Execution), PRD 5.3 (Document Source API placeholder).

3.  **Task 1.3: Enhance Error Handling in Orchestrator for Search API Failures**
    *   **Action:** Update the `try...catch` blocks in `researchAgentOrchestrator.ts` around the search API calls.
    *   **Details:**
        *   Specifically catch errors that might be thrown by `executeExaSearch` (e.g., API rate limits, invalid queries for Exa, network issues).
        *   Send appropriate `ResearchUpdate` objects of `type: "ERROR"` with informative messages specific to search failures (e.g., "Failed to retrieve documents from Exa: [error message]").
        *   Decide on pipeline behavior: should it halt, or attempt to proceed with zero documents if search fails? (PRD implies proceeding, then assessment would likely suggest human review or new queries).
    *   **Acceptance Criteria:**
        *   ✅ Orchestrator gracefully handles errors from the search API.
        *   ✅ Clear error messages are streamed to the client if document retrieval fails.
    *   **PRD Alignment:** NFR3.1 (Reliability).

4.  **Task 1.4: Initial Testing of Live Search Integration**
    *   **Action:** Perform basic end-to-end tests by inputting simple legal questions in the UI.
    *   **Details:**
        *   Focus on whether the `GENERATING_QUERIES` stage completes, `exaSearchUtil.ts` logs successful calls (if you add logging there), and the `FETCHING_DOCUMENTS` stage in the orchestrator receives non-empty `searchResultItems` (or an empty array if the query genuinely yields no results).
        *   Monitor console logs on both server and client for errors.
    *   **Acceptance Criteria:**
        *   ✅ The orchestrator can complete the `FETCHING_DOCUMENTS` stage using live search results.
        *   ✅ Basic queries return some results, and "no results please" type queries (if Exa supports similar negative constraints) return empty arrays.

**Checkpoint 1 (End of Search API Integration):** The application can now fetch real documents based on AI-generated queries. The `analyzedDocsSummaryAtom` on the client should start receiving data based on these live documents (though the analysis itself might still need tuning).

### Phase 2: End-to-End Data Flow Validation and BAML Prompt Refinement

**Goal:** Ensure that real document data flows correctly through the entire BAML pipeline and that BAML function prompts are effective with this live data.

**Tasks:**

1.  **Task 2.1: Validate and Refine `AnalyzeSingleDocument` with Live Data**
    *   **Action:** Test the `AnalyzeSingleDocument` BAML function with various real documents retrieved in Phase 1. Refine its prompt and/or client-friendly data mapping in the orchestrator.
    *   **Details:**
        *   Run research tasks with diverse legal questions to get varied `SearchResultItem` inputs (different lengths, sources, content types).
        *   Observe the `AnalyzedDocument` BAML output (e.g., using BAML Playground, VSCode debugger, or server-side logs in the orchestrator).
        *   Check:
            *   Relevance and confidence scores: Are they reasonable?
            *   Summaries: Are they accurate and concise?
            *   Key arguments, entities, quotes: Are they correctly extracted?
            *   Reasoning: Is the LLM's reasoning sound?
        *   If outputs are poor, iterate on the prompt in `baml_src/functions/2-analyze_document.baml`.
        *   Adjust the mapping in `researchAgentOrchestrator.ts` for the `DATA` update of stage `ANALYZING_DOCUMENTS` to ensure client-friendly summaries are effective.
        *   Update `2-analyze_document.test.baml` with new test cases based on real document characteristics.
    *   **Acceptance Criteria:**
        *   ✅ `AnalyzeSingleDocument` produces consistently reasonable structured output for a variety of live legal documents.
        *   ✅ Client-side `ClientAnalyzedDoc` objects are populated correctly with relevant snippets and scores.
        *   ✅ BAML tests for `AnalyzeSingleDocument` are updated and pass.
    *   **PRD Alignment:** FR1.1.2, FR2.3.3.

2.  **Task 2.2: Validate and Refine `SynthesizeAllFindings` with Live Data**
    *   **Action:** Test `SynthesizeAllFindings` with collections of `AnalyzedDocument` objects derived from live data. Refine its prompt.
    *   **Details:**
        *   Focus on scenarios with 2-5 `AnalyzedDocument` inputs.
        *   Check:
            *   Quality of `key_synthesized_topics`: Are themes relevant and well-articulated?
            *   `synthesis` content: Is it a good summary drawing from multiple documents?
            *   `supporting_document_ids`: Are they correct?
            *   `confidence_score` for topics: Are they appropriate given input document relevance?
            *   `unanswered_aspects` and `emerging_questions`: Are these insightful?
        *   Iterate on the prompt in `baml_src/functions/3-synthesize_findings.baml`.
        *   Update `3-synthesize_findings.test.baml`.
    *   **Acceptance Criteria:**
        *   ✅ `SynthesizeAllFindings` produces coherent and relevant synthesis from live analyzed documents.
        *   ✅ Client-side `ClientSynthesis` is populated correctly.
        *   ✅ BAML tests are updated and pass.
    *   **PRD Alignment:** FR1.1.3.

3.  **Task 2.3: Validate and Refine `AssessResearchAndPlanNextSteps` with Live Data**
    *   **Action:** Test `AssessResearchAndPlanNextSteps` with live `LegalQueryAnalysis` and `OverallSynthesis` objects. Refine its prompt, especially the decision tree logic.
    *   **Details:**
        *   Ensure the highly structured prompt in `baml_src/core_loop.baml` (with its mandatory decision tree and sufficiency criteria) works reliably with real-data inputs.
        *   Test scenarios that should lead to different `NextActionType` outputs (GENERATE_REPORT, REFINE_QUERIES, NEW_QUERIES, etc.).
        *   Verify that `suggested_queries_for_refinement` or `document_ids_for_deeper_analysis` are populated correctly when appropriate.
        *   Iterate on the prompt in `baml_src/core_loop.baml`.
        *   Update `core_loop.test.baml`.
    *   **Acceptance Criteria:**
        *   ✅ `AssessResearchAndPlanNextSteps` makes consistent and logical decisions based on real data inputs.
        *   ✅ The LLM adheres to the explicit decision tree and sufficiency criteria in the prompt.
        *   ✅ BAML tests are updated and pass.
    *   **PRD Alignment:** FR1.1.4, FR2.5.1.

4.  **Task 2.4: Validate and Refine `GenerateFinalLegalReport` (Streaming) with Live Data**
    *   **Action:** Test `b.stream.GenerateFinalLegalReport` with live `OverallSynthesis`. Refine its prompt and ensure streaming output is handled correctly by the orchestrator.
    *   **Details:**
        *   Check quality of `report_title`, `executive_summary`, `sections[].content`, `conclusion`.
        *   Verify that streaming fields (marked with `@stream.with_state` in BAML types like `FinalLegalReport` and `LegalReportSection`) are indeed streamed progressively by the LLM.
        *   Ensure the orchestrator's logic for consuming this BAML stream and re-streaming chunks as `ResearchUpdate.data` (with `fieldName`, `isFieldComplete`) works correctly.
        *   Iterate on the prompt in `baml_src/functions/4-generate_final_report.baml`.
        *   Update `4-generate_final_report.test.baml`.
    *   **Acceptance Criteria:**
        *   ✅ `GenerateFinalLegalReport` produces a well-structured and coherent report from live synthesis data.
        *   ✅ Streaming fields are generated progressively by the LLM.
        *   ✅ The server orchestrator correctly handles the BAML stream and relays chunks to the client for fields like `executiveSummary` and `sections[i].content`.
        *   ✅ BAML tests are updated and pass.
    *   **PRD Alignment:** FR1.1.5, FR2.3.4.

**Checkpoint 2 (End of BAML Refinement):** All BAML functions in the pipeline are tested and refined with live data. The server orchestrator correctly processes their outputs, including handling BAML streams.

### Phase 3: Dynamic UI Population and Refinement

**Goal:** Ensure all UI components dynamically display data sourced from the live pipeline via Jotai atoms and that streaming text updates are smooth.

**Tasks:**

1.  **Task 3.1: Full UI Population for `EvidenceAnalysis.tsx`**
    *   **Action:** Ensure all fields in the `EvidenceAnalysis` component (list and detail panel) are populated from `analyzedDocsSummaryAtom` and `selectedAnalyzedDocIdAtom`, which now contain data derived from live documents.
    *   **Details:**
        *   Verify display of: `title`, `url` (or source), `relevanceScore`, `summarySnippet` (streaming).
        *   **Extended Data:** Ensure `keyArguments`, `extractedEntities` (with correct styling via `getEntityStyle`), `extractedQuotes`, `fullText` (truncated), `counterArguments` are all displayed if present in `ClientAnalyzedDoc`.
        *   Test the "View Analysis Reasoning" button to open `AnalysisReasoningModal` and display `selectedDocument.analysisReasoning` correctly.
    *   **Acceptance Criteria:**
        *   ✅ `EvidenceAnalysis` list and detail panel fully reflect the content of `ClientAnalyzedDoc` objects derived from live data.
        *   ✅ Streaming of `summarySnippet` (and other potential text fields) is smooth.
        *   ✅ `AnalysisReasoningModal` displays the correct summarized reasoning.
    *   **PRD Alignment:** FR5.3.

2.  **Task 3.2: Full UI Population for `SynthesisReporting.tsx` & `ReportDrafter.tsx`**
    *   **Action:** Ensure these components are fully dynamic based on `synthesisDetailsAtom` and `finalReportContentAtom`.
    *   **Details:**
        *   **Synthesis Studio Tab:**
            *   Display `synthesis.topics` (title, synthesisSnippet (streaming), confidence, doc IDs).
            *   Display `synthesis.unansweredAspects` and `synthesis.emergingQuestions`.
            *   "View Synthesis Reasoning" button should open `SynthesisReasoningModal` and display `synthesis.reasoningSummary`.
        *   **Report Drafter Tab:**
            *   Display `report.title` (editable).
            *   Document Structure outline should correctly reflect completion status of `executiveSummary`, `sections`, `conclusion` based on whether their content in `finalReportContentAtom` is non-empty.
            *   Main content area should render `report.executiveSummary`, `report.sections[].content`, and `report.conclusion` with progressive streaming updates.
    *   **Acceptance Criteria:**
        *   ✅ "Synthesis Studio" accurately displays live synthesis data, with streaming snippets.
        *   ✅ "Report Drafter" accurately displays the live report content, with all designated fields streaming progressively.
        *   ✅ Document structure outline in `ReportDrafter` dynamically reflects content completion.
    *   **PRD Alignment:** FR5.4, FR5.5.

3.  **Task 3.3: Dynamic Content for `GuidanceStrategy.tsx` Agent Assessment**
    *   **Action:** Populate the "Agent Assessment" section in `GuidanceStrategy.tsx` with dynamic data from `AssessResearchAndPlanNextSteps` (via a dedicated Jotai atom if necessary, or from `researchStatusAtom.message` / `synthesisDetailsAtom` if simple).
    *   **Details:**
        *   The `ResearchUpdate.data` payload for the `ASSESSING_RESEARCH` stage should contain `isSufficient`, `assessmentSummary`, `nextAction`, `identifiedGaps`, `suggestedRefinementQueries`.
        *   `useResearchAgent` needs to store this `ClientResearchAssessment` data in a new Jotai atom (e.g., `researchAssessmentAtom`).
        *   `GuidanceStrategy.tsx` should consume this atom to display the assessment details.
    *   **Acceptance Criteria:**
        *   ✅ "Agent Assessment" section dynamically shows `assessmentSummary`, `nextAction`, and relevant details (gaps, suggested queries) from the live pipeline.
    *   **PRD Alignment:** FR5.2.3.

4.  **Task 3.4: UI/UX Review for Streaming and Loading States**
    *   **Action:** Conduct a thorough review of the entire UI during a live research process.
    *   **Details:**
        *   Ensure all loading spinners, disabled states, and progress messages (e.g., "Analyzing document 3/5") are accurate and provide a smooth user experience.
        *   Verify that streaming text (summaries, report content) updates progressively without UI jitter or layout shifts. The caret animation in `app/globals.css` should be visible on actively streaming text.
        *   Check responsiveness of non-streaming UI elements (scrolling, opening unrelated modals) while data is streaming.
    *   **Acceptance Criteria:**
        *   ✅ UI provides clear, consistent, and non-blocking feedback during all stages of the research process.
        *   ✅ Streaming text enhances UX by showing progress.
    *   **PRD Alignment:** NFR1.2, NFR1.3, NFR4.6.1.

**Checkpoint 3 (End of UI Integration):** The application's UI is fully dynamic, driven by real data from the BAML pipeline via Jotai state. All core features are visually functional with live data.
