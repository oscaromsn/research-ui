## 4. Error Handling

### 4.1 Error Definition

#### Core Principle

All custom errors MUST be defined using `Data.TaggedError` or `Schema.TaggedError` for type-safe error handling. Never use plain `Error` objects or throw exceptions within Effect code.

#### Data.TaggedError

Use `Data.TaggedError` for internal domain errors that don't need serialization:

```typescript
import { Data } from "effect"

// Basic error with context
class UserNotFoundError extends Data.TaggedError("UserNotFoundError")<{
  readonly userId: string
}> {}

// Error with rich context
class ValidationError extends Data.TaggedError("ValidationError")<{
  readonly field: string
  readonly message: string
  readonly value?: unknown
  readonly constraints?: Record<string, unknown>
}> {}

// Error with cause preservation
class DatabaseError extends Data.TaggedError("DatabaseError")<{
  readonly message: string
  readonly operation: string
  readonly cause?: unknown
}> {}

// Usage in Effect
const getUser = (id: string): Effect.Effect<User, UserNotFoundError | DatabaseError> =>
  Effect.gen(function* () {
    const result = yield* db.users.findById(id).pipe(
      Effect.mapError((cause) => 
        new DatabaseError({ 
          message: "Failed to fetch user",
          operation: "findById",
          cause 
        })
      )
    )
    
    if (!result) {
      return yield* Effect.fail(new UserNotFoundError({ userId: id }))
    }
    
    return result
  })
```

#### Schema.TaggedError

Use `Schema.TaggedError` for errors that cross API boundaries or need serialization:

```typescript
import { Schema } from "@effect/schema"

// Serializable API error
export class ApiError extends Schema.TaggedError<ApiError>()(
  "ApiError",
  {
    status: Schema.Number,
    message: Schema.String,
    code: Schema.optional(Schema.String),
    details: Schema.optional(Schema.Unknown)
  }
) {}

// Validation error with schema enforcement
export class SchemaValidationError extends Schema.TaggedError<SchemaValidationError>()(
  "SchemaValidationError",
  {
    errors: Schema.Array(Schema.Struct({
      path: Schema.Array(Schema.String),
      message: Schema.String
    }))
  }
) {}

// Usage with HTTP endpoints
const createUser = (input: unknown): Effect.Effect<User, ApiError> =>
  Effect.gen(function* () {
    const validated = yield* Schema.decodeUnknown(UserSchema)(input).pipe(
      Effect.mapError((parseError) =>
        new ApiError({
          status: 400,
          message: "Invalid user data",
          code: "VALIDATION_ERROR",
          details: parseError
        })
      )
    )
    
    return yield* db.users.create(validated).pipe(
      Effect.mapError((cause) =>
        new ApiError({
          status: 500,
          message: "Failed to create user",
          code: "DATABASE_ERROR"
        })
      )
    )
  })
```

#### Error Naming Conventions

Follow these naming patterns for consistency:

```typescript
// ✅ CORRECT: PascalCase with Error suffix
class UserNotFoundError extends Data.TaggedError("UserNotFoundError")<{}> {}
class InvalidCredentialsError extends Data.TaggedError("InvalidCredentialsError")<{}> {}
class RateLimitExceededError extends Data.TaggedError("RateLimitExceededError")<{}> {}

// ❌ WRONG: Missing Error suffix or incorrect casing
class UserNotFound extends Data.TaggedError("UserNotFound")<{}> {}
class invalidCredentials extends Data.TaggedError("invalidCredentials")<{}> {}
class RATE_LIMIT_ERROR extends Data.TaggedError("RATE_LIMIT_ERROR")<{}> {}
```

**Naming Patterns:**
- **Resource Errors**: `{Resource}NotFoundError`, `{Resource}AlreadyExistsError`
- **Operation Errors**: `{Operation}FailedError`, `{Operation}TimeoutError`
- **Validation Errors**: `{Field}ValidationError`, `Invalid{Field}Error`
- **Authorization Errors**: `Unauthorized{Operation}Error`, `Forbidden{Resource}Error`
- **System Errors**: `{System}ConnectionError`, `{System}TimeoutError`

### 4.2 Error Modeling Strategies

#### Typed Errors (E Channel)

Use typed errors in the error channel (`E` in `Effect<A, E, R>`) for **recoverable** domain failures:

```typescript
// ✅ GOOD: Typed errors for recoverable failures
class AuthenticationError extends Data.TaggedError("AuthenticationError")<{
  readonly reason: string
}> {}

class RateLimitError extends Data.TaggedError("RateLimitError")<{
  readonly retryAfter: number
  readonly remainingAttempts: number
}> {}

class ValidationError extends Data.TaggedError("ValidationError")<{
  readonly errors: ReadonlyArray<string>
}> {}

// Business operation with typed errors
const authenticateUser = (
  credentials: Credentials
): Effect.Effect<Session, AuthenticationError | RateLimitError | ValidationError> =>
  Effect.gen(function* () {
    // Validate input
    if (!credentials.username || !credentials.password) {
      return yield* Effect.fail(
        new ValidationError({ errors: ["Username and password required"] })
      )
    }
    
    // Check rate limit
    const remaining = yield* rateLimiter.checkLimit(credentials.username)
    if (remaining === 0) {
      return yield* Effect.fail(
        new RateLimitError({ 
          retryAfter: 60, 
          remainingAttempts: 0 
        })
      )
    }
    
    // Authenticate
    const session = yield* authService.authenticate(credentials).pipe(
      Effect.mapError(() => 
        new AuthenticationError({ reason: "Invalid credentials" })
      )
    )
    
    return session
  })
```

**When to use typed errors:**
- Authentication/authorization failures
- Business rule violations
- Validation failures
- Rate limiting
- Resource not found (when recovery is possible)
- External service unavailable (with retry logic)

#### Defects (die/dieMessage)

Use defects for **unrecoverable** errors indicating bugs or contract violations:

```typescript
import { Effect } from "effect"

// ✅ GOOD: Defects for programming errors
const processPayload = (data: unknown): Effect.Effect<Processed> =>
  Effect.gen(function* () {
    // Parse from trusted source - should never fail
    const parsed = yield* Schema.decodeUnknown(PayloadSchema)(data).pipe(
      Effect.catchAll((parseError) =>
        Effect.die(
          new Error(`Contract violation: Invalid payload from trusted source`, {
            cause: parseError
          })
        )
      )
    )
    
    // Impossible state - should never happen
    if (parsed.items.length === 0) {
      return yield* Effect.die(
        new Error("Impossible state: Empty items array after validation")
      )
    }
    
    return yield* process(parsed)
  })

// Using dieMessage for simple cases
const unsafeOperation = (value: number): Effect.Effect<number> =>
  value > 0
    ? Effect.succeed(value)
    : Effect.dieMessage("Expected positive number, got negative")
```

**When to use defects:**
- Parse errors from trusted/internal sources
- Contract violations
- Impossible states after validation
- Programming errors (null pointer, out of bounds)
- Configuration errors at startup
- Infrastructure failures that shouldn't be retried

#### Generic vs Specific Errors

**Decision Matrix:**

| Use Case | Error Strategy | Example |
|----------|---------------|---------|
| **Module-level operations** | Generic module error | `KeyHashError` for all KeyHash operations |
| **Different recovery strategies** | Specific error types | `UserNotFoundError`, `InvalidCredentialsError` |
| **Simple error reason** | Generic with message | `OperationError({ message: "..." })` |
| **Complex error context** | Specific typed errors | Domain-specific error with structured data |

```typescript
// ✅ GOOD: Generic module error for simple cases
export class KeyHashError extends Data.TaggedError("KeyHashError")<{
  readonly message: string
  readonly cause?: unknown
}> {}

export const fromBytes = (bytes: Uint8Array): Effect.Effect<KeyHash, KeyHashError> =>
  Effect.gen(function* () {
    if (bytes.length !== KEYHASH_BYTES_LENGTH) {
      return yield* Effect.fail(
        new KeyHashError({
          message: `KeyHash must be ${KEYHASH_BYTES_LENGTH} bytes long, got: ${bytes.length}`
        })
      )
    }
    
    if (!isValidHex(bytes)) {
      return yield* Effect.fail(
        new KeyHashError({
          message: "KeyHash must contain valid hexadecimal bytes"
        })
      )
    }
    
    return new KeyHash({ bytes })
  })

// ✅ GOOD: Specific errors for different handling
class UserNotFoundError extends Data.TaggedError("UserNotFoundError")<{
  readonly userId: string
}> {}

class UserSuspendedError extends Data.TaggedError("UserSuspendedError")<{
  readonly userId: string
  readonly suspendedUntil: Date
  readonly reason: string
}> {}

class UserDeletedError extends Data.TaggedError("UserDeletedError")<{
  readonly userId: string
  readonly deletedAt: Date
}> {}

const getUser = (
  id: string
): Effect.Effect<User, UserNotFoundError | UserSuspendedError | UserDeletedError> =>
  Effect.gen(function* () {
    const result = yield* db.users.findById(id)
    
    if (!result) {
      return yield* Effect.fail(new UserNotFoundError({ userId: id }))
    }
    
    if (result.status === "suspended") {
      return yield* Effect.fail(
        new UserSuspendedError({
          userId: id,
          suspendedUntil: result.suspendedUntil,
          reason: result.suspensionReason
        })
      )
    }
    
    if (result.status === "deleted") {
      return yield* Effect.fail(
        new UserDeletedError({
          userId: id,
          deletedAt: result.deletedAt
        })
      )
    }
    
    return result
  })

// Different recovery strategies for each error
const getUserWithFallback = (id: string) =>
  getUser(id).pipe(
    Effect.catchTags({
      UserNotFoundError: () => Effect.succeed(guestUser),
      UserSuspendedError: (error) => 
        Effect.fail(new UnauthorizedError({ 
          message: `Account suspended until ${error.suspendedUntil}` 
        })),
      UserDeletedError: () => 
        Effect.fail(new GoneError({ message: "Account deleted" }))
    })
  )
```

### 4.3 Error Recovery Patterns

#### Catching Specific Errors

```typescript
import { Effect } from "effect"

// ✅ PREFERRED: Handle single error type with catchTag
const getUserSafely = (id: string) =>
  getUser(id).pipe(
    Effect.catchTag("UserNotFoundError", (error) =>
      Effect.succeed({
        id: error.userId,
        name: "Guest User",
        email: "guest@example.com"
      })
    )
  )

// ✅ PREFERRED: Handle multiple errors with catchTags
const getUserWithRecovery = (id: string) =>
  getUser(id).pipe(
    Effect.catchTags({
      UserNotFoundError: (error) =>
        Effect.log(`User ${error.userId} not found, using guest`).pipe(
          Effect.as(guestUser)
        ),
      UserSuspendedError: (error) =>
        Effect.fail(
          new UnauthorizedError({
            message: `Account suspended: ${error.reason}`,
            code: "ACCOUNT_SUSPENDED"
          })
        ),
      UserDeletedError: () =>
        Effect.fail(
          new GoneError({
            message: "Account has been deleted",
            code: "ACCOUNT_DELETED"
          })
        )
    })
  )

// ✅ CONDITIONAL: Handle errors based on conditions
const retryableOperation = fetchData().pipe(
  Effect.catchIf(
    (error) => 
      error._tag === "NetworkError" && error.statusCode >= 500,
    (error) => 
      Effect.log(`Retryable error: ${error.message}`).pipe(
        Effect.flatMap(() => Effect.retry(fetchData(), { times: 3 }))
      )
  )
)

// ❌ AVOID: Using catchAll except at application boundary
const badPattern = operation().pipe(
  Effect.catchAll((error) => {
    // Catches everything including defects!
    // Loses type information about errors
    return Effect.succeed(fallback)
  })
)
```

#### Recovering from Errors

```typescript
// Provide default value on error
const withDefault = <A>(
  effect: Effect.Effect<A, E>,
  defaultValue: A
): Effect.Effect<A> =>
  effect.pipe(
    Effect.catchAll(() => Effect.succeed(defaultValue))
  )

// Usage
const settings = getUserSettings(userId).pipe(
  Effect.catchAll(() => Effect.succeed(defaultSettings))
)

// Retry with exponential backoff
const reliableFetch = (url: string) =>
  fetch(url).pipe(
    Effect.retry({
      while: (error) => error._tag === "NetworkError",
      times: 3,
      schedule: Schedule.exponential("100 millis")
    })
  )

// Fallback to alternative source
const dataWithFallback = getPrimaryData(id).pipe(
  Effect.catchAll(() => getBackupData(id)),
  Effect.catchAll(() => getCachedData(id)),
  Effect.catchAll(() => Effect.succeed(emptyData))
)

// Provide alternative approach
const orderWithRetry = submitOrder(order).pipe(
  Effect.catchTag("PaymentGatewayError", () =>
    Effect.log("Primary payment failed, trying backup").pipe(
      Effect.flatMap(() => submitOrderWithBackupPayment(order))

  )
)

// Timeout with default
const withTimeout = <A>(
  effect: Effect.Effect<A, E>,
  duration: Duration.Duration,
  defaultValue: A
): Effect.Effect<A, E> =>
  effect.pipe(
    Effect.timeout(duration),
    Effect.map(Option.getOrElse(() => defaultValue))
  )
```

### 4.4 Error Control Flow

#### Railway-Oriented Programming

Effect implements railway-oriented programming where operations flow on success and errors automatically propagate:

```typescript
// ✅ Automatic error propagation (Railway Pattern)
const processOrder = (orderId: string) =>
  Effect.gen(function* () {
    // Success track
    const order = yield* getOrder(orderId)           // If fails, stops here
    const validated = yield* validateOrder(order)     // If fails, stops here
    const payment = yield* processPayment(validated)  // If fails, stops here
    const shipped = yield* shipOrder(payment)         // If fails, stops here
    
    return shipped // Only reached if all succeed
  })

// All errors automatically propagate without explicit handling
// Type: Effect<Order, OrderNotFoundError | ValidationError | PaymentError | ShippingError>

// Add error handling at the boundaries
const orderEndpoint = (orderId: string) =>
  processOrder(orderId).pipe(
    Effect.catchTags({
      OrderNotFoundError: (error) =>
        Effect.succeed({
          status: 404,
          message: `Order ${error.orderId} not found`
        }),
      ValidationError: (error) =>
        Effect.succeed({
          status: 400,
          message: error.message
        }),
      PaymentError: (error) =>
        Effect.succeed({
          status: 402,
          message: "Payment failed"
        }),
      ShippingError: () =>
        Effect.succeed({
          status: 500,
          message: "Shipping failed"
        })
    })
  )
```

**Railway Pattern Benefits:**
1. **Automatic short-circuiting**: First error stops execution
2. **No nested try-catch**: Errors flow through the type system
3. **Explicit error types**: All possible failures in the signature
4. **Composable error handling**: Add recovery at any level

#### Effect.flip Pattern

Use `Effect.flip` to convert the error channel to success channel for testing or explicit error handling:

```typescript
// Testing error scenarios
const testErrorCase = Effect.gen(function* () {
  const error = yield* getUser("invalid-id").pipe(Effect.flip)
  
  // Now error is in success channel, can be used normally
  expect(error._tag).toBe("UserNotFoundError")
  expect(error.userId).toBe("invalid-id")
})

// Explicit error handling as values
const handleAsValue = Effect.gen(function* () {
  const result = yield* riskyOperation().pipe(Effect.flip)
  
  // Process error as a value
  switch (result._tag) {
    case "NetworkError":
      yield* Effect.log("Network error occurred")
      return yield* retryOperation()
    case "ValidationError":
      yield* Effect.log("Validation failed")
      return yield* useDefaultValue()
  }
})

// Dual track processing
const processEither = Effect.gen(function* () {
  const either = yield* operation().pipe(Effect.either)
  
  return Either.match(either, {
    onLeft: (error) => `Failed: ${error._tag}`,
    onRight: (success) => `Success: ${success}`
  })
})
```

#### Typed Errors for Control Flow

Use typed errors to signal different control flow states instead of returning boolean flags:

```typescript
// ❌ ANTI-PATTERN: Using flags for control flow
class TokenRefreshResult extends Schema.Class<TokenRefreshResult>(

)({
  success: Schema.Boolean,
  shouldRetry: Schema.Boolean,
  tokens: Schema.optional(TokenSchema)
}) {}

const badRefresh = (): Effect.Effect<TokenRefreshResult> =>
  Effect.gen(function* () {
    // Caller must manually check flags
    return new TokenRefreshResult({
      success: true,
      shouldRetry: true,
      tokens: newTokens
    })
  })

// Caller has to check flags manually
const badUsage = Effect.gen(function* () {
  const result = yield* badRefresh()
  
  if (result.shouldRetry) {
    // Manual retry logic
    return yield* originalRequest()
  }
  
  if (!result.success) {
    // Manual error handling
  }
})

// ✅ GOOD PATTERN: Using typed errors for control flow
class ForceRetryError extends Data.TaggedError("ForceRetryError")<{
  readonly reason: string
}> {}

class TokenRefreshError extends Data.TaggedError("TokenRefreshError")<{
  readonly reason: string
}> {}

const goodRefresh = (): Effect.Effect<Tokens, ForceRetryError | TokenRefreshError> =>
  Effect.gen(function* () {
    const newTokens = yield* fetchNewTokens()
    
    // Signal retry through error channel
    return yield* Effect.fail(
      new ForceRetryError({ reason: "Token refreshed, retry original request" })
    )
  })

// Declarative retry based on error type
const goodUsage = Effect.gen(function* () {
  return yield* originalRequest()
}).pipe(
  Effect.catchTag("UnauthorizedError", () => goodRefresh()),
  Effect.retry({
    while: (error) => error._tag === "ForceRetryError"
  })
)

// More complex control flow example
class RequiresUserConsentError extends Data.TaggedError("RequiresUserConsentError")<{
  readonly permissions: ReadonlyArray<string>
}> {}

class RequiresReauthenticationError extends Data.TaggedError("RequiresReauthenticationError")<{
  readonly lastAuthTime: Date
}> {}

const operation = (): Effect.Effect
  Result,
  RequiresUserConsentError | RequiresReauthenticationError
> =>
  Effect.gen(function* () {
    const session = yield* getSession()
    
    if (session.permissions.length === 0) {
      return yield* Effect.fail(
        new RequiresUserConsentError({ permissions: ["read", "write"] })
      )
    }
    
    if (isSessionExpired(session)) {
      return yield* Effect.fail(
        new RequiresReauthenticationError({ lastAuthTime: session.lastAuth })
      )
    }
    
    return yield* performOperation()
  })

// Caller handles different control flows declaratively
const handleOperation = operation().pipe(
  Effect.catchTags({
    RequiresUserConsentError: (error) =>
      Effect.gen(function* () {
        yield* requestUserConsent(error.permissions)
        return yield* operation() // Retry after consent
      }),
    RequiresReauthenticationError: () =>
      Effect.gen(function* () {
        yield* reauthenticateUser()
        return yield* operation() // Retry after reauth
      })
  })
)
```

**Benefits of Typed Errors for Control Flow:**
1. **Declarative intent**: Error type clearly signals what should happen
2. **Type-safe handling**: Compiler ensures all cases handled
3. **Composable retry logic**: Built-in `Effect.retry` with error predicates
4. **Self-documenting**: Error types document control flow requirements

```typescript
  effect.pipe(
    Effect.mapError((cause) =>
      new LayerError({
        layer,
        operation: "unknown", // Can be enhanced with span information
        cause,
        timestamp: Date.now()
      })
    )
  )

  Effect.gen(function* () {
    // Data access logic
  }).pipe(withErrorBoundary("DataLayer"))

const businessLayer = (operation: string) =>
  Effect.gen(function* () {
    // Business logic
  }).pipe(withErrorBoundary("BusinessLayer"))

const apiLayer = (operation: string) =>
  Effect.gen(function* () {
    // API logic
  }).pipe(withErrorBoundary("ApiLayer"))

// Compose with boundaries
const fullOperation = Effect.gen(function* () {
  const data = yield* dataLayer("fetch")
  const processed = yield* businessLayer("process")
  return yield* apiLayer("respond")
})

// Transform boundary errors at application edge

  Effect.catchTag("LayerError", (error) =>
    Effect.gen(function* () {
      yield* Effect.logError(`Error in ${error.layer}`, {

        operation: error.operation,
```

```typescript
const logErrorByType = <E extends { _tag: string }>(
  error: E,
  context: Record<string, unknown>
) =>
  Effect.gen(function* () {
    const baseLog = {
      errorTag: error._tag,
      error,
      ...context,
      timestamp: Date.now()
    }
    
    // Different log levels based on error type
    if (error._tag === "ValidationError") {
      yield* Effect.logWarning("Validation failed", baseLog)
    } else if (error._tag === "UnauthorizedError") {
      yield* Effect.logWarning("Unauthorized access attempt", baseLog)
    } else if (error._tag === "DatabaseError") {
      yield* Effect.logError("Database error", baseLog)
    } else {
      yield* Effect.logFatal("Critical error", baseLog)
    }
  })

// Integration with error handling

  effect: Effect.Effect<A, E, R>,
  context: Record<string, unknown>
): Effect.Effect<A, E, R> =>
  effect.pipe(
    Effect.tapError((error) => logErrorByType(error, context))
  )
```

### 4.6 Error Messages

#### Message Clarity

Error messages MUST clearly communicate:
1. **What happened**: The specific failure that occurred
2. **Relevant context**: Input values, state, or conditions
3. **Expected vs actual**: What was expected and what was received

```typescript
// ✅ GOOD: Clear, contextual error messages
class ValidationError extends Data.TaggedError("ValidationError")<{
  readonly field: string
  readonly value: unknown
  readonly constraint: string
  readonly expected: string
}> {
  get message(): string {
    return `Validation failed for field '${this.field}': ` +
           `Expected ${this.expected}, but received: ${JSON.stringify(this.value)}. ` +
           `Constraint: ${this.constraint}`
  }
}

// Usage with clear context
const validateAge = (age: unknown): Effect.Effect<number, ValidationError> =>

        new ValidationError({
          field: "age",
          value: age,
          constraint: "must be a number between 0 and 150",
          expected: "number in range [0, 150]"

class BadError extends Data.TaggedError("BadError")<{
  message: string
```

#### Production vs Development Messages

Adjust error message verbosity based on environment:

```typescript
class ApplicationError extends Data.TaggedError("ApplicationError")<{
  readonly message: string
  readonly code: string
  readonly context?: Record<string, unknown>
  readonly cause?: unknown
}> {
  toString(): string {
    const isDevelopment = process.env.NODE_ENV === "development"
    
    if (isDevelopment) {
      // Detailed error information for development
      return [
        `[${this.code}] ${this.message}`,
        this.context ? `Context: ${JSON.stringify(this.context, null, 2)}` : "",
        this.cause ? `Cause: ${this.cause}` : "",
        this.cause instanceof Error ? `Stack: ${this.cause.stack}` : ""
      ].filter(Boolean).join("\n")
    } else {
      // Minimal error information for production
      return `[${this.code}] ${this.message}`
    }
  }
}

// Usage
const handleRequest = (input: unknown) =>
  Effect.gen(function* () {
    // Operation that may fail
  }).pipe(
    Effect.mapError((cause) =>
      new ApplicationError({
        message: "Request processing failed",
        code: "REQUEST_FAILED",
        context: process.env.NODE_ENV === "development" 
          ? { input, timestamp: Date.now() }
          : undefined,
        cause
      })
    )
  )

// Safe error formatting for API responses
const formatErrorForClient = (error: ApplicationError) => ({
  error: {
    code: error.code,
    message: error.message,
    // Never expose internal details in production
    ...(process.env.NODE_ENV === "development" && {
      details: error.context,
      timestamp: Date.now()
    })
  }
})
```

### Best Practices Summary

1. **Error Definition:**
   - Use `Data.TaggedError` for internal errors
   - Use `Schema.TaggedError` for serializable errors
   - Follow naming conventions: `{Domain}{Type}Error`

2. **Error Modeling:**
   - Typed errors for recoverable failures
   - Defects for programming errors and contract violations
   - Generic errors when error reason is sufficient
   - Specific errors when different recovery strategies needed

3. **Error Recovery:**
   - Use `catchTag`/`catchTags` for specific error handling
   - Avoid `catchAll` except at application boundaries
   - Implement retry strategies for transient failures
   - Provide fallbacks for optional operations

4. **Error Control Flow:**
   - Let errors propagate automatically (railway pattern)
   - Use typed errors instead of boolean flags
   - Use `Effect.flip` for testing error scenarios

5. **Error Context:**
   - Enrich errors with relevant context
   - Create error boundaries for different layers
   - Log errors with full cause chains
   - Preserve stack traces for debugging

6. **Error Messages:**
   - Clear: State what happened with context
   - Actionable: Provide guidance on fixing issues
   - Environment-aware: Detailed in dev, minimal in prod
   - Preserve cause: Include original error information

7. **Error Testing:**
   - Test all error scenarios
   - Use mock services with controllable behavior
   - Verify error recovery strategies
   - Test error transformation and enrichment
