# 19. Anti-Patterns & Common Mistakes

This section identifies common pitfalls and anti-patterns when working with Effect-TS, providing clear guidance on what to avoid and how to write correct, maintainable code.

## 19.1 Critical Anti-Patterns

These patterns are **absolutely forbidden** and will cause critical bugs or break Effect's fundamental guarantees.

### 🚨 FORBIDDEN: try-catch in Effect.gen

**Problem**: Using `try-catch` inside `Effect.gen` completely bypasses Effect's typed error channel and breaks the entire error handling system.

**Why It's Broken**:
- Effect errors flow through the `E` channel, not JavaScript exceptions
- `try-catch` only catches JavaScript exceptions, not Effect failures
- Breaks interruption safety and resource management
- Loses all type safety for errors
- The catch block will **never be reached** for Effect failures

```typescript
// ❌ ABSOLUTELY FORBIDDEN - This is fundamentally broken
const processData = (data: string) =>
  Effect.gen(function* () {
    try {
      // This try-catch is completely useless for Effect errors
      const result = yield* parseData(data) // If this fails, catch won't run!
      return result
    } catch (error) {
      // ❌ This will NEVER execute for Effect failures
      // This only catches JavaScript exceptions, not Effect errors
      return "fallback"
    }
  })

// ❌ WRONG: Even for synchronous operations
const badParse = Effect.gen(function* () {
  try {
    return JSON.parse(invalidJson) // Don't do this!
  } catch (e) {
    return yield* Effect.fail(new ParseError())
  }
})
```

**✅ CORRECT PATTERNS**:

```typescript
import { Effect, Either, Exit } from "effect"

// ✅ Option 1: Use Effect.try for synchronous code that may throw
const parseJson = (input: string) =>
  Effect.try({
    try: () => JSON.parse(input),
    catch: (error) => new JsonParseError({ cause: error })
  })

// ✅ Option 2: Use Effect.tryPromise for async operations
const fetchData = (url: string) =>
  Effect.tryPromise({
    try: () => fetch(url).then(r => r.json()),
    catch: (error) => new NetworkError({ cause: error })
  })

// ✅ Option 3: Use Effect.either for explicit error handling
const processDataSafely = (data: string) =>
  Effect.gen(function* () {
    const result = yield* Effect.either(parseData(data))
    
    if (Either.isLeft(result)) {
      // Handle the typed error
      yield* Effect.log("Parse failed", result.left)
      return "fallback"
    }
    
    return result.right
  })

// ✅ Option 4: Use Effect.catchTag to handle specific errors
const processWithRecovery = (data: string) =>
  parseData(data).pipe(
    Effect.catchTag("ParseError", (error) => 
      Effect.succeed("fallback")
    )
  )

// ✅ Option 5: Use Effect.exit for granular control
const processWithFullControl = (data: string) =>
  Effect.gen(function* () {
    const exit = yield* Effect.exit(parseData(data))
    
    if (Exit.isFailure(exit)) {
      // Inspect the full Cause
      const cause = exit.cause
      yield* Effect.log("Failed with cause", cause)
      return "fallback"
    }
    
    return exit.value
  })
```

**Key Principle**: Effect's error channel (`E`) is separate from JavaScript exceptions. Use Effect's error handling combinators, never try-catch.

### 🚨 FORBIDDEN: Type Assertions

**Problem**: Type assertions (`as any`, `as never`, `as unknown`) destroy TypeScript's type safety and hide real type errors that Effect's type system is designed to prevent.

**Why It's Dangerous**:
- Masks underlying type problems instead of fixing them
- Creates false sense of security
- Primary source of runtime bugs
- Defeats the entire purpose of using TypeScript and Effect
- Makes refactoring dangerous and error-prone

```typescript
// ❌ ABSOLUTELY FORBIDDEN PATTERNS
const processUser = (data: unknown) => {
  const user = data as User  // ❌ Destroys type safety
  return user.name.toUpperCase()
}

const dangerousOperation = () => {
  const result = complexComputation() as any  // ❌ Hides all type information
  return result.someProperty
}

const workaroundTypeError = () => {
  const value = problematicFunction() as never  // ❌ Usually a hack to bypass checks
  return value
}

// ❌ WRONG: Using unknown to bypass type checking
const badPattern = (input: unknown) => {
  const typed = input as UserData  // Skips validation!
  return processUserData(typed)
}
```

**✅ CORRECT APPROACH - Fix the Root Cause**:

```typescript
import { Schema } from "@effect/schema"
import { Effect } from "effect"

// ✅ Option 1: Use Schema to safely parse unknown data
const UserSchema = Schema.Struct({
  id: Schema.String,
  name: Schema.String,
  email: Schema.String
})

const processUser = (data: unknown) =>
  Effect.gen(function* () {
    // Type-safe parsing with proper error handling
    const user = yield* Schema.decodeUnknown(UserSchema)(data)
    return user.name.toUpperCase()
  })

// ✅ Option 2: Fix the function signature
interface ComplexResult {
  value: number
  metadata: Record<string, string>
}

const safeOperation = (): Effect.Effect<ComplexResult, ComputationError> =>
  Effect.gen(function* () {
    const result = yield* complexComputation()
    return result  // Properly typed
  })

// ✅ Option 3: Use proper generic type parameters
const typeSafeWrapper = <A>(effect: Effect.Effect<A>) =>
  effect.pipe(
    Effect.map(result => ({ data: result }))
  )

// ✅ Option 4: Import correct types
import { HttpClientResponse } from "@effect/platform"

const fetchUser = (id: string) =>
  httpClient.get(`/users/${id}`).pipe(
    HttpClientResponse.schemaBodyJson(UserSchema)  // Properly typed
  )

// ✅ Option 5: Adjust function signatures to match usage
const properlyTypedFunction = (
  input: User  // Explicitly require what you need
): Effect.Effect<string, never> =>
  Effect.succeed(input.name.toUpperCase())
```

**When You Think You Need Type Assertions**:
1. **Check if there's a proper Schema** - Use Schema.decodeUnknown for unknown data
2. **Fix the function signature** - Make the types match reality
3. **Import the right types** - Ensure you're using correct type definitions
4. **Use proper generics** - Leverage TypeScript's type parameters
5. **Narrow types properly** - Use type guards and refinements

**The Only Valid Use**: Using `satisfies` operator to ensure objects conform to types without widening:

```typescript
// ✅ CORRECT: Use satisfies, not as
const config = {
  port: 3000,
  host: "localhost"
} satisfies ServerConfig  // Type-checks without widening types
```

### 🚨 MANDATORY: Return Yield Pattern for Terminal Effects

**Problem**: Forgetting `return` before `yield*` for terminal effects leads to unreachable code and incorrect type narrowing.

**Why It Matters**:
- Makes termination explicit to the compiler
- Enables proper TypeScript control flow analysis
- Prevents unreachable code warnings
- Makes code intent clear to readers
- Required for proper type narrowing

```typescript
// ❌ WRONG: Missing return before terminal effects
const processOrder = (order: Order) =>
  Effect.gen(function* () {
    if (!order.items.length) {
      // ❌ Missing return! Code below is incorrectly considered reachable
      yield* Effect.fail(new EmptyOrderError())
    }
    
    // TypeScript thinks this is reachable, but it's not!
    const total = yield* calculateTotal(order)
    return total
  })

// ❌ WRONG: Missing return for interrupts
const cancellableOperation = Effect.gen(function* () {
  const shouldCancel = yield* checkCancellation()
  
  if (shouldCancel) {
    yield* Effect.interrupt  // ❌ Missing return
  }
  
  // Unreachable code!
  yield* performOperation()
})

// ❌ WRONG: Missing return for die
const processWithValidation = (data: unknown) =>
  Effect.gen(function* () {
    const parsed = yield* Schema.decodeUnknown(DataSchema)(data).pipe(
      Effect.catchTag("ParseError", (error) => {
        // ❌ This should return yield*
        yield* Effect.die(error)  // ParseError means contract violation
      })
    )
    return parsed
  })
```

**✅ CORRECT PATTERNS**:

```typescript
// ✅ CORRECT: Always use return yield* for errors
const processOrder = (order: Order) =>
  Effect.gen(function* () {
    if (!order.items.length) {
      // ✅ Explicit termination with return yield*
      return yield* Effect.fail(new EmptyOrderError())
    }
    
    // TypeScript knows we have items here
    const total = yield* calculateTotal(order)
    return total
  })

// ✅ CORRECT: Return yield* for interrupts
const cancellableOperation = Effect.gen(function* () {
  const shouldCancel = yield* checkCancellation()
  
  if (shouldCancel) {
    // ✅ Makes termination explicit
    return yield* Effect.interrupt
  }
  
  // TypeScript knows shouldCancel is false here
  return yield* performOperation()
})

// ✅ CORRECT: Return yield* for die
const processWithValidation = (data: unknown) =>
  Effect.gen(function* () {
    const parsed = yield* Schema.decodeUnknown(DataSchema)(data).pipe(
      Effect.catchTag("ParseError", (error) => {
        // ✅ Proper termination for defects
        return yield* Effect.die(error)
      })
    )
    return parsed
  })

// ✅ CORRECT: Multiple conditional failures
const validateUser = (user: User) =>
  Effect.gen(function* () {
    if (!user.email) {
      return yield* Effect.fail(new ValidationError({ field: "email" }))
    }
    
    if (user.age < 0) {
      return yield* Effect.fail(new ValidationError({ field: "age" }))
    }
    
    if (!user.name.trim()) {
      return yield* Effect.fail(new ValidationError({ field: "name" }))
    }
    
    // All validations passed, TypeScript knows this
    return user
  })
```

**Rule of Thumb**: If you're yielding a terminal effect (`Effect.fail`, `Effect.die`, `Effect.interrupt`), always use `return yield*`.

### Effect.run* Inside Other Effects

**Problem**: Using `Effect.runSync`, `Effect.runPromise`, or `Effect.runFork` inside other effects breaks composition and Effect's guarantees.

**Why It's Wrong**:
- Breaks error propagation
- Loses interruption safety
- Prevents resource cleanup
- Defeats dependency injection
- Makes code untestable
- Violates Effect's composability

```typescript
// ❌ WRONG: Running effects inside effects
const processData = Effect.gen(function* () {
  // ❌ Breaks composition - errors can't propagate properly
  const user = Effect.runSync(getUser("123"))
  
  // ❌ Loses all Effect guarantees
  const data = await Effect.runPromise(fetchData(user.id))
  
  return processUserData(user, data)
})

// ❌ WRONG: Nested runPromise
const badPattern = Effect.gen(function* () {
  const results = yield* Effect.all(
    ids.map(id => Effect.promise(() => 
      // ❌ Don't run effects inside Promise constructors
      Effect.runPromise(fetchData(id))
    ))
  )
  return results
})

// ❌ WRONG: Using runFork inside effects
const forkingInside = Effect.gen(function* () {
  // ❌ Use Effect.fork instead
  Effect.runFork(backgroundTask())
  
  return yield* mainTask()
})
```

**✅ CORRECT PATTERNS**:

```typescript
// ✅ CORRECT: Compose effects naturally
const processData = Effect.gen(function* () {
  // ✅ Just yield* - errors propagate properly
  const user = yield* getUser("123")
  const data = yield* fetchData(user.id)
  return processUserData(user, data)
})

// ✅ CORRECT: Use Effect.all for parallel operations
const fetchAllData = (ids: string[]) =>
  Effect.all(
    ids.map(id => fetchData(id)),
    { concurrency: "unbounded" }
  )

// ✅ CORRECT: Use Effect.fork for background tasks
const withBackgroundTask = Effect.gen(function* () {
  // ✅ Effect.fork returns a Fiber you can manage
  const fiber = yield* Effect.fork(backgroundTask())
  
  const result = yield* mainTask()
  
  // Optionally wait for background task
  yield* Fiber.join(fiber)
  
  return result
})

// ✅ CORRECT: Run effects only at the application boundary
const program = Effect.gen(function* () {
  const user = yield* getUser("123")
  const data = yield* fetchData(user.id)
  return processUserData(user, data)
})

// ✅ Run at the edge of your application
Effect.runPromise(
  program.pipe(Effect.provide(AppLayer))
).then(console.log)
```

**Key Principle**: Effect.run\* should only appear at the absolute edge of your application, where you're interfacing with the non-Effect world.

### Multiple Effect.provide Calls

**Problem**: Using multiple `Effect.provide` calls breaks Layer memoization and creates separate service scopes.

**Why It's Problematic**:
- Breaks Layer memoization guarantees
- Creates multiple instances of the same service
- Wastes resources (multiple database connections, etc.)
- Loses shared state between service instances
- Makes caching ineffective
- Breaks service lifecycle management

```typescript
// ❌ WRONG: Multiple provide calls create separate scopes
const badProgram = Effect.gen(function* () {
  const user = yield* getUser("123")
  return user
}).pipe(
  Effect.provide(DatabaseLive),      // ❌ First scope
  Effect.provide(LoggerLive),         // ❌ Second scope - new DB instance!
  Effect.provide(CacheLive),          // ❌ Third scope - new DB AND Logger!
  Effect.provide(UserServiceLive)     // ❌ Fourth scope - everything recreated!
)

// ❌ WRONG: Providing dependencies at different levels
const operation1 = effect1.pipe(Effect.provide(DatabaseLive))
const operation2 = effect2.pipe(Effect.provide(DatabaseLive))  // Different DB instance!

const combined = Effect.all([operation1, operation2])  // Two separate DB connections!
```

**✅ CORRECT PATTERNS**:

```typescript
// ✅ CORRECT: Compose all layers first, then provide once
const AppLayer = Layer.mergeAll(
  DatabaseLive,
  LoggerLive,
  CacheLive,
  UserServiceLive
)

// ✅ Single Effect.provide at the application boundary
const program = Effect.gen(function* () {
  const user = yield* getUser("123")
  return user
}).pipe(
  Effect.provide(AppLayer)  // ✅ Single scope, all services memoized
)

// ✅ CORRECT: Compose layers using Layer composition operators
const AppLayer = Layer.empty.pipe(
  Layer.provide(DatabaseLive),
  Layer.provide(LoggerLive),
  Layer.provideMerge(CacheLive),
  Layer.provideMerge(UserServiceLive)
)

// ✅ CORRECT: Share layer across multiple operations
const layer = Layer.mergeAll(DatabaseLive, LoggerLive)

const operation1 = effect1.pipe(Effect.provide(layer))
const operation2 = effect2.pipe(Effect.provide(layer))

// ✅ Both operations share the same service instances

// ✅ CORRECT: Provide once at the top level
Effect.runPromise(
  Effect.all([
    getUserProfile("123"),
    getUserOrders("123"),
    getUserPreferences("123")
  ]).pipe(
    Effect.provide(AppLayer)  // ✅ All operations share services
  )
)
```

**Best Practice**: Build your complete application layer once using `Layer.mergeAll` or `Layer.provideMerge`, then provide it exactly once at the top level of your program.

### Manual Fiber Management

**Problem**: Manually forking, tracking, and joining fibers when high-level APIs like `Effect.all` and `Effect.race` would be clearer and safer.

**Why Avoid It**:
- Error-prone and verbose
- Easy to leak fibers
- Miss interruption handling
- Harder to read and maintain
- High-level APIs handle edge cases correctly

```typescript
// ❌ AVOID: Manual fiber management
const manualParallel = Effect.gen(function* () {
  // ❌ Verbose and error-prone
  const fiber1 = yield* Effect.fork(task1())
  const fiber2 = yield* Effect.fork(task2())
  const fiber3 = yield* Effect.fork(task3())
  
  // ❌ Easy to forget error handling
  const result1 = yield* Fiber.join(fiber1)
  const result2 = yield* Fiber.join(fiber2)
  const result3 = yield* Fiber.join(fiber3)
  
  return [result1, result2, result3]
})

// ❌ AVOID: Manual racing
const manualRace = Effect.gen(function* () {
  const fiber1 = yield* Effect.fork(source1())
  const fiber2 = yield* Effect.fork(source2())
  
  // ❌ Complex and error-prone
  const result1 = yield* Fiber.await(fiber1).pipe(Effect.option)
  
  if (result1._tag === "Some") {
    yield* Fiber.interrupt(fiber2)
    return result1.value
  }
  
  return yield* Fiber.join(fiber2)
})
```

**✅ CORRECT: Use High-Level APIs**:

```typescript
// ✅ CORRECT: Use Effect.all for parallel execution
const parallel = Effect.all([
  task1(),
  task2(),
  task3()
], { concurrency: "unbounded" })

// ✅ CORRECT: Use Effect.race for racing
const raced = Effect.race(
  source1(),
  source2()
)

// ✅ CORRECT: Use Effect.forEach for iterating
const processed = Effect.forEach(
  items,
  processItem,
  { concurrency: 5 }
)

// ✅ CORRECT: Use Effect.raceAll for multiple sources
const firstSuccess = Effect.raceAll([
  primarySource(),
  backupSource(),
  fallbackSource()
])
```

**When Manual Fiber Management Is Acceptable**:
- Building low-level abstractions or primitives
- Implementing custom concurrency patterns
- Need precise control over fiber lifecycle

**For 95% of cases**: Use `Effect.all`, `Effect.race`, `Effect.forEach`, etc.

### Ignoring Defects

**Problem**: Using `Effect.catchAll` indiscriminately to catch defects that should be allowed to crash the fiber.

**Why It's Wrong**:
- Defects indicate bugs or contract violations
- Should not be recovered from
- Hiding defects makes debugging harder
- Violates fail-fast principle
- Can lead to corrupt state

```typescript
// ❌ WRONG: Catching all errors including defects
const badHandler = someEffect.pipe(
  Effect.catchAll((error) => {
    // ❌ This catches defects too!
    console.log("Handled error:", error)
    return Effect.succeed(defaultValue)
  })
)

// ❌ WRONG: Silently swallowing defects
const silentFailure = riskyOperation.pipe(
  Effect.catchAllCause(() => Effect.void)  // ❌ Hides everything!
)

// ❌ WRONG: Converting defects to success
const hidingBugs = parseData(data).pipe(
  Effect.catchAll(() => Effect.succeed(null))  // ❌ Parse errors are defects!
)
```

**✅ CORRECT PATTERNS**:

```typescript
// ✅ CORRECT: Catch only specific typed errors
const goodHandler = someEffect.pipe(
  Effect.catchTag("UserNotFound", (error) =>
    Effect.succeed(guestUser)
  ),
  Effect.catchTag("ValidationError", (error) =>
    Effect.fail(new BadRequestError({ cause: error }))
  )
  // Defects and other errors propagate up
)

// ✅ CORRECT: Let defects crash the fiber
const letDefectsCrash = riskyOperation.pipe(
  Effect.catchTag("ExpectedError", handleExpectedError)
  // Parse errors, type errors, etc. will crash - as they should
)

// ✅ CORRECT: Die on contract violations
const strictParsing = HttpClientResponse.schemaBodyJson(Schema).pipe(
  Effect.catchTag("ParseError", (error) =>
    Effect.die(error)  // API contract violated
  )
)

// ✅ CORRECT: Handle defects only at the top level for logging
const program = myApplication.pipe(
  Effect.catchAllDefect((defect) =>
    Effect.gen(function* () {
      // Log the defect for monitoring
      yield* Effect.logFatal("Application defect", defect)
      // Then let it crash or restart the process
      return yield* Effect.die(defect)
    })
  )
)
```

**Key Principle**: Typed errors in the `E` channel are for expected failures you can recover from. Defects are for bugs and should crash the fiber.

### Global State Outside Effect

**Problem**: Using global mutable variables instead of Effect's state management primitives.

**Why It's Wrong**:
- Breaks testability
- Prevents composability
- Race conditions in concurrent code
- Hard to reason about state changes
- Violates functional programming principles

```typescript
// ❌ WRONG: Global mutable state
let requestCount = 0  // ❌ Global state

const incrementRequests = Effect.sync(() => {
  requestCount++  // ❌ Side effect outside Effect system
})

const getRequestCount = Effect.sync(() => requestCount)

// ❌ WRONG: Global object state
const globalCache: Record<string, unknown> = {}  // ❌ Global mutable

const cacheValue = (key: string, value: unknown) =>
  Effect.sync(() => {
    globalCache[key] = value  // ❌ Untraceable mutation
  })

// ❌ WRONG: Singleton pattern with state
class GlobalCounter {
  private static instance: GlobalCounter
  private count = 0  // ❌ Hidden global state
  
  static getInstance() {
    if (!this.instance) {
      this.instance = new GlobalCounter()
    }
    return this.instance
  }
  
  increment() { this.count++ }
  getCount() { return this.count }
}
```

**✅ CORRECT PATTERNS**:

```typescript
import { Effect, Ref, Layer, Context } from "effect"

// ✅ CORRECT: Use Ref for mutable state within Effect
const makeCounter = Effect.gen(function* () {
  const count = yield* Ref.make(0)
  
  return {
    increment: Ref.update(count, n => n + 1),
    get: Ref.get(count),
    reset: Ref.set(count, 0)
  } as const
})

// ✅ CORRECT: Encapsulate state in a service
class CounterService extends Context.Tag("CounterService")
  CounterService,
  {
    readonly increment: Effect.Effect<void>
    readonly get: Effect.Effect<number>
    readonly reset: Effect.Effect<void>
  }
>() {}

const CounterServiceLive = Layer.effect(
  CounterService,
  Effect.gen(function* () {
    const count = yield* Ref.make(0)
    
    return {
      increment: Ref.update(count, n => n + 1),
      get: Ref.get(count),
      reset: Ref.set(count, 0)
    }
  })
)

// ✅ CORRECT: Use within Effect programs
const program = Effect.gen(function* () {
  const counter = yield* CounterService
  
  yield* counter.increment
  yield* counter.increment
  
  const count = yield* counter.get
  yield* Effect.log(`Count: ${count}`)
})

// ✅ CORRECT: Cache as a service with Ref
class CacheService extends Context.Tag("CacheService")
  CacheService,
  {
    readonly get: (key: string) => Effect.Effect<unknown | null>
    readonly set: (key: string, value: unknown) => Effect.Effect<void>
  }
>() {}

const CacheServiceLive = Layer.effect(
  CacheService,
  Effect.gen(function* () {
    const cache = yield* Ref.make<Map<string, unknown>>(new Map())
    
    return {
      get: (key) => Ref.get(cache).pipe(
        Effect.map(map => map.get(key) ?? null)
      ),
      set: (key, value) => Ref.update(cache, map => 
        new Map(map).set(key, value)
      )
    }
  })
)
```

**Benefits of Effect State Management**:
- Thread-safe by default
- Testable with mock services
- Composable across your application
- Clear state boundaries
- Proper cleanup and lifecycle

## 19.2 Performance Anti-Patterns

These patterns lead to poor performance, resource exhaustion, or scalability issues.

### No Concurrency Limits

**Problem**: Running unbounded concurrent operations without limits can exhaust system resources.

**Why It's Problematic**:
- Memory exhaustion from too many concurrent operations
- Database connection pool exhaustion
- API rate limit violations
- CPU thrashing from context switching
- System instability

```typescript
// ❌ WRONG: Unbounded concurrency on large datasets
const processAllUsers = (userIds: string[]) =>
  Effect.all(
    userIds.map(id => processUser(id)),
    { concurrency: "unbounded" }  // ❌ Could be millions of users!
  )

// ❌ WRONG: No limit on concurrent API calls
const fetchAllData = (urls: string[]) =>
  Effect.all(
    urls.map(url => fetch(url)),  // ❌ Could hit rate limits
    { concurrency: "unbounded" }
  )

// ❌ WRONG: Unlimited database queries
const getAllRecords = (ids: string[]) =>
  Effect.all(
    ids.map(id => db.query(`SELECT * FROM records WHERE id = ?`, id)),
    { concurrency: "unbounded" }  // ❌ Exhausts connection pool
  )
```

**✅ CORRECT: Set Appropriate Limits**:

```typescript
// ✅ CORRECT: Reasonable concurrency limit
const processAllUsers = (userIds: string[]) =>
  Effect.all(
    userIds.map(id => processUser(id)),
    { concurrency: 10 }  // ✅ Process 10 at a time
  )

// ✅ CORRECT: Respect API rate limits
const fetchAllData = (urls: string[]) =>
  Effect.all(
    urls.map(url => fetchWithRetry(url)),
    { concurrency: 5 }  // ✅ Stay within rate limits
  )

// ✅ CORRECT: Use Semaphore for database access
const makeDbService = Effect.gen(function* () {
  const pool = yield* createPool()
  const semaphore = yield* Effect.makeSemaphore(pool.maxConnections)
  
  const query = (sql: string) =>
    semaphore.withPermits(1)(
      Effect.tryPromise(() => pool.query(sql))
    )
  
  return { query }
})

// ✅ CORRECT: Batch processing with controlled concurrency
const processBatch = <A>(items: A[], process: (item: A) => Effect.Effect<void>) =>
  Effect.forEach(
    items,
    process,
    { 
      concurrency: 50,      // Process 50 at a time
      batching: true        // Optimize for batch operations
    }
  )
```

**Guidelines for Setting Concurrency**:
- **Database operations**: Match connection pool size (usually 10-50)
- **API calls**: Respect rate limits (usually 5-10)
- **CPU-bound work**: Match CPU core count
- **I/O-bound work**: Higher limits acceptable (50-100)
- **Default safe value**: 10-20 concurrent operations

### No Caching Strategy

**Problem**: Repeatedly computing or fetching the same data without caching.

**Why It's Problematic**:
- Unnecessary database queries
- Redundant API calls
- Wasted CPU cycles
- Increased latency
- Higher costs

```typescript
// ❌ WRONG: No caching for expensive operations
const getUser = (id: string) =>
  Effect.gen(function* () {
    // ❌ Database query every single time
    const user = yield* db.query("SELECT * FROM users WHERE id = ?", id)
    return user
  })

// Each call hits the database, even for the same ID
const program = Effect.gen(function* () {
  const user1 = yield* getUser("123")  // DB query
  const user2 = yield* getUser("123")  // DB query again!
  const user3 = yield* getUser("123")  // DB query again!
})

// ❌ WRONG: No caching for computed values
const expensiveComputation = (input: string) =>
  Effect.gen(function* () {
    yield* Effect.sleep("5 seconds")  // Expensive operation
```

### Redundant Database Queries (N+1 Problem)

**Problem**: Making separate database queries in a loop instead of batching.

**Why It's Critical**:
- Exponential slowdown with data growth
- Network round-trip overhead for each query
- Database connection exhaustion
- Locks and contention issues

```typescript
// ❌ WRONG: N+1 query problem
const getUsersWithPosts = (userIds: string[]) =>
  Effect.gen(function* () {
    const users = yield* Effect.all(
      userIds.map(id => db.query("SELECT * FROM users WHERE id = ?", id))
      // ❌ N queries for N users
    )
    
    const usersWithPosts = yield* Effect.all(
      users.map(user =>
        Effect.gen(function* () {
          const posts = yield* db.query(
            "SELECT * FROM posts WHERE user_id = ?",
            user.id
          )  // ❌ Another N queries!
          
          return { ...user, posts }
        })
      )
    )
    
    return usersWithPosts
  })
// Total queries: 2N (1 + 1 per user)
```

**✅ CORRECT: Batch Queries**:

```typescript
// ✅ CORRECT: Single batched query
const getUsersWithPosts = (userIds: string[]) =>
  Effect.gen(function* () {
    // ✅ Single query for all users
    const users = yield* db.query(
      `SELECT * FROM users WHERE id IN (${userIds.map(() => '?').join(',')})`,
      userIds
    )
    
    // ✅ Single query for all posts
    const posts = yield* db.query(
      `SELECT * FROM posts WHERE user_id IN (${userIds.map(() => '?').join(',')})`,
      userIds
    )
    
    // Join in memory
    return users.map(user => ({
      ...user,
      posts: posts.filter(post => post.user_id === user.id)
    }))
  })
// Total queries: 2 (constant, regardless of N)

// ✅ CORRECT: Use RequestResolver for automatic batching
interface GetUser extends Request.Request<User, UserNotFoundError> {
  readonly _tag: "GetUser"
  readonly id: string
}

const GetUser = Request.tagged<GetUser>("GetUser")

const UserResolver = RequestResolver.makeBatched(
  (requests: GetUser[]) =>
    Effect.gen(function* () {
      const ids = requests.map(req => req.id)
      
      // ✅ Single batched query
      const users = yield* db.query(
        `SELECT * FROM users WHERE id IN (${ids.map(() => '?').join(',')})`,
        ids
      )
      
      return Effect.forEach(requests, req => {
        const user = users.find(u => u.id === req.id)
        return user
          ? Request.succeed(req, user)
          : Request.fail(req, new UserNotFoundError({ userId: req.id }))
      })
    })
)

// Automatic batching!
const getUsers = (ids: string[]) =>
  Effect.all(
    ids.map(id => Effect.request(GetUser({ id }), UserResolver))
  )
```

5. **Use events** for decoupling (event-driven architecture)

**Problem**: Not using Layer composition for managing service dependencies.

## 19.4 Testing Anti-Patterns

These patterns lead to flaky, unmaintainable, or ineffective tests.

### Using Wrong Testing Framework

**Problem**: Using regular `vitest` for Effect code or vice versa.

**Critical Rule**:
- Use `@effect/vitest` for Effect-based code
- Use regular `vitest` for pure TypeScript functions

```typescript
// ❌ WRONG: Using vitest expect for Effect tests
import { describe, expect, it } from "vitest"

it("should get user", async () => {
  const result = await Effect.runPromise(getUser("123"))
  expect(result.id).toBe("123")  // ❌ Wrong assertion style
})

// ❌ WRONG: Using Effect.runSync in regular it()
it("should process data", () => {
  const result = Effect.runSync(processData("input"))  // ❌ Breaks Effect guarantees
  expect(result).toBe("output")
})

// ❌ WRONG: Using @effect/vitest for pure functions
import { assert, it } from "@effect/vitest"

it("should add numbers", () => {
  const result = add(1, 2)  // ❌ Pure function, use regular vitest
  assert.strictEqual(result, 3)
})
```

**✅ CORRECT: Use Appropriate Framework**:

```typescript
// ✅ CORRECT: Use @effect/vitest for Effect code
import { assert, describe, it } from "@effect/vitest"

describe("UserService", () => {
  it.effect("should get user", () =>
    Effect.gen(function* () {
      const user = yield* getUser("123")
      
      // ✅ Use assert methods
      assert.strictEqual(user.id, "123")
      assert.deepStrictEqual(user, expectedUser)
    })
  )
  
  it.effect("should handle errors", () =>
    Effect.gen(function* () {
      // ✅ Use Effect.flip to test errors
      const error = yield* getUser("invalid").pipe(Effect.flip)
      
      assert.strictEqual(error._tag, "UserNotFoundError")
    })
  )
})

// ✅ CORRECT: Use regular vitest for pure functions
import { describe, expect, it } from "vitest"

describe("Pure Functions", () => {
  it("should add numbers", () => {
    const result = add(1, 2)
    expect(result).toBe(3)
  })
  
  it("should format string", () => {
    const result = formatString("hello")
    expect(result).toBe("HELLO")
  })
})
```

### Not Using TestClock

**Problem**: Using real time in tests, leading to slow and flaky tests.

```typescript
// ❌ WRONG: Using real time delays
it.effect("should retry after delay", () =>
  Effect.gen(function* () {
    const start = Date.now()
    
    yield* operation.pipe(
      Effect.retry({ 
        times: 3, 
        schedule: Schedule.spaced("1 second")  // ❌ Real 3 second delay!
      })
    )
    
    const elapsed = Date.now() - start
    assert.isTrue(elapsed >= 3000)  // ❌ Test takes 3+ seconds
  })
)

// ❌ WRONG: Actual sleep in tests

  Effect.gen(function* () {
    yield* Effect.sleep("5 seconds")  // ❌ Test takes 5 seconds!
    
    const result = yield* checkState()
    assert.strictEqual(result, "completed")
  })
)
```

**✅ CORRECT: Use TestClock**:

```typescript
import { TestClock } from "effect/TestClock"

// ✅ CORRECT: Fast-forward time with TestClock
it.effect("should retry after delay", () =>
  Effect.gen(function* () {
    const fiber = yield* Effect.fork(
      operation.pipe(
        Effect.retry({ 
          times: 3, 
          schedule: Schedule.spaced("1 second")
        })
      )
    )
    
    // ✅ Instantly advance time
    yield* TestClock.adjust("3 seconds")
    
    const result = yield* Fiber.join(fiber)
    assert.strictEqual(result, expected)
  }).pipe(Effect.provide(TestClock.TestClock))
)

// ✅ CORRECT: Test timeouts with TestClock
it.effect("should timeout correctly", () =>
  Effect.gen(function* () {
    const fiber = yield* Effect.fork(
      longOperation().pipe(Effect.timeout("5 seconds"))
    )
    
    // ✅ Fast-forward past timeout
    yield* TestClock.adjust("6 seconds")
    
    const result = yield* Fiber.join(fiber)
    assert.isTrue(Option.isNone(result))  // Timed out
  }).pipe(Effect.provide(TestClock.TestClock))
)

// ✅ CORRECT: Test scheduled operations
it.effect("should execute at scheduled time", () =>
  Effect.gen(function* () {
    let executed = false
    
    const fiber = yield* Effect.fork(
      Effect.sleep("10 seconds").pipe(
        Effect.flatMap(() => 
          Effect.sync(() => { executed = true })
        )
      )
    )
    
    // Not executed yet
    assert.isFalse(executed)
    
    // Fast-forward time
    yield* TestClock.adjust("10 seconds")
    
    yield* Fiber.join(fiber)
    
    // Now executed
    assert.isTrue(executed)
  }).pipe(Effect.provide(TestClock.TestClock))
)
```

**TestClock Usage Guidelines**:
- **Always use** for tests involving time
- **Advance time** explicitly with `TestClock.adjust`
- **Provide TestClock layer** to test programs
- **Never use** real `Effect.sleep` without TestClock in tests

### Flaky Tests

**Problem**: Tests that pass/fail non-deterministically.

**Common Causes**:
- Race conditions
- Relying on real time
- Order-dependent tests
- Shared mutable state
- External dependencies

```typescript
// ❌ WRONG: Race condition in test
it.effect("processes items concurrently", () =>
  Effect.gen(function* () {
    const results: string[] = []
    
    yield* Effect.all([
      Effect.sync(() => results.push("a")),  // ❌ Race condition!
      Effect.sync(() => results.push("b")),
      Effect.sync(() => results.push("c"))
    ])
    
    assert.deepStrictEqual(results, ["a", "b", "c"])  // ❌ Flaky! Order varies
  })
)

// ❌ WRONG: Shared mutable state

  Effect.gen(function* () {
    counter++
    assert.strictEqual(counter, 1)  // ❌ Fails if test 2 runs first
  })
)

it.effect("test 2", () =>
  Effect.gen(function* () {
    counter++
    assert.strictEqual(counter, 1)  // ❌ Depends on execution order
  })
)

// ❌ WRONG: Relying on external state
it.effect("fetches user", () =>
  Effect.gen(function* () {
    const user = yield* httpClient.get("/users/123")  // ❌ Real API call!
    assert.strictEqual(user.name, "John")
  })
)
```

**✅ CORRECT: Deterministic Tests**:

```typescript
  })

        yield* latch.await
        results.push("b")

        results.push("start")
```

```typescript
    yield* service.increment()
    
    // ✅ Test through public API
    const count = yield* service.getCount()
    assert.strictEqual(count, 2)
  })
)
```

**Principles**:
- Test **what** the code does, not **how** it does it
- Test through **public APIs** only
- Test **observable behavior** and effects
- Don't test implementation details like:
  - Which database queries are executed
  - Which cache methods are called
  - Internal state structure
  - Private methods
  - Number of function calls

### No Mock Layers

**Problem**: Not using mock layers for testing, leading to slow tests and external dependencies.

```typescript
// ❌ WRONG: Testing with real database
it.effect("creates user", () =>
  Effect.gen(function* () {
    const service = yield* UserService
    
    // ❌ This hits the real database!
    const user = yield* service.createUser({
      name: "John",
      email: "john@example.com"
    })
    
    assert.strictEqual(user.name, "John")
  }).pipe(
    Effect.provide(DatabaseLive)  // ❌ Real database connection
  )
)

// ❌ WRONG: Testing with real HTTP client
it.effect("fetches weather", () =>
  Effect.gen(function* () {
    const service = yield* WeatherService
    
    // ❌ Makes real API call!
    const weather = yield* service.getWeather("New York")
    
    assert.isDefined(weather.temperature)
  }).pipe(
    Effect.provide(HttpClientLive)  // ❌ Real HTTP client
  )
)
```

**✅ CORRECT: Use Mock Layers**:

```typescript
// ✅ CORRECT: Mock database layer
const MockDatabase = Layer.succeed(Database, {
  query: (sql: string, params: unknown[]) =>
    Effect.succeed({
      id: "test-id",
      name: "John",
      email: "john@example.com"
    })
})

it.effect("creates user", () =>
  Effect.gen(function* () {
    const service = yield* UserService
    
    // ✅ Uses mock database
    const user = yield* service.createUser({
      name: "John",
      email: "john@example.com"
    })
    
    assert.strictEqual(user.name, "John")
  }).pipe(
    Effect.provide(
      Layer.mergeAll(
        MockDatabase,
        UserServiceLive
      )
    )
  )
)

// ✅ CORRECT: Mock HTTP client
const MockHttpClient = Layer.succeed(HttpClient, {
  get: (url: string) =>
    Effect.succeed({
      temperature: 72,
      conditions: "Sunny"
    })
})

it.effect("fetches weather", () =>
  Effect.gen(function* () {
    const service = yield* WeatherService
    
    // ✅ Uses mock HTTP client
    const weather = yield* service.getWeather("New York")
    
    assert.strictEqual(weather.temperature, 72)
  }).pipe(
    Effect.provide(
      Layer.mergeAll(
        MockHttpClient,
        WeatherServiceLive
      )
    )
  )
)

// ✅ CORRECT: Controllable mock behavior
const makeMockDatabase = (behavior: "success" | "error") =>
  Layer.succeed(Database, {
    query: (sql: string, params: unknown[]) =>
      behavior === "success"
        ? Effect.succeed(mockData)
        : Effect.fail(new DatabaseError({ operation: "query" }))
  })

it.effect("handles database errors", () =>
  Effect.gen(function* () {
    const service = yield* UserService
    
    const error = yield* service.getUser("123").pipe(Effect.flip)
    
    assert.strictEqual(error._tag, "DatabaseError")
  }).pipe(
    Effect.provide(
      Layer.mergeAll(
        makeMockDatabase("error"),
        UserServiceLive
      )
    )
  )
)
```

**Benefits of Mock Layers**:
- Fast tests (no I/O)
- Deterministic behavior
- No external dependencies
- Controllable failure scenarios
- Easy to test error paths

### Ignoring Error Paths

**Problem**: Only testing happy paths, not error scenarios.

```typescript
// ❌ WRONG: Only testing success
describe("UserService", () => {
  it.effect("gets user", () =>
    Effect.gen(function* () {
      const user = yield* service.getUser("123")
      assert.strictEqual(user.id, "123")
    })
  )
  
  // ❌ No tests for:
  // - User not found
  // - Database errors
  // - Invalid IDs
  // - Network failures
})
```

**✅ CORRECT: Test All Paths**:

```typescript
describe("UserService", () => {
  describe("getUser", () => {
    // ✅ Success case
    it.effect("returns user when found", () =>
      Effect.gen(function* () {
        const user = yield* service.getUser("123")
        assert.strictEqual(user.id, "123")
      }).pipe(Effect.provide(mockSuccessLayer))
    )
    
    // ✅ Error case: Not found
    it.effect("fails when user not found", () =>
      Effect.gen(function* () {
        const error = yield* service.getUser("invalid").pipe(Effect.flip)
        
        assert.strictEqual(error._tag, "UserNotFoundError")
        assert.strictEqual(error.userId, "invalid")
      }).pipe(Effect.provide(mockNotFoundLayer))
    )
    
    // ✅ Error case: Database error
    it.effect("fails on database error", () =>
      Effect.gen(function* () {
        const error = yield* service.getUser("123").pipe(Effect.flip)
        
        assert.strictEqual(error._tag, "DatabaseError")
      }).pipe(Effect.provide(mockDatabaseErrorLayer))
    )
    
    // ✅ Edge case: Invalid input
    it.effect("handles invalid ID format", () =>
      Effect.gen(function* () {
        const error = yield* service.getUser("").pipe(Effect.flip)
        
        assert.strictEqual(error._tag, "ValidationError")
      })
    )
  })
  
  describe("createUser", () => {
    // ✅ Success case
    it.effect("creates user with valid data", () =>
      Effect.gen(function* () {
        const user = yield* service.createUser(validData)
        assert.isDefined(user.id)
      })
    )
    
    // ✅ Validation errors
    it.effect("fails with invalid email", () =>
      Effect.gen(function* () {
        const error = yield* service.createUser({
          ...validData,
          email: "invalid"
        }).pipe(Effect.flip)
        
        assert.strictEqual(error._tag, "ValidationError")
        assert.strictEqual(error.field, "email")
      })
    )
    
    it.effect("fails with duplicate email", () =>
      Effect.gen(function* () {
        const error = yield* service.createUser(existingUser).pipe(Effect.flip)
        
        assert.strictEqual(error._tag, "DuplicateEmailError")
      })
    )
    
    // ✅ Database errors
    it.effect("handles database connection failure", () =>
      Effect.gen(function* () {
        const error = yield* service.createUser(validData).pipe(Effect.flip)
        
        assert.strictEqual(error._tag, "DatabaseError")
      }).pipe(Effect.provide(mockConnectionErrorLayer))
    )
  })
})
```

**Error Path Testing Checklist**:
- ✅ Expected errors (validation, not found, etc.)
- ✅ Database/network failures
- ✅ Invalid input formats
- ✅ Boundary conditions (empty, null, very large)
- ✅ Concurrent access issues
- ✅ Resource exhaustion scenarios
- ✅ Timeout conditions
- ✅ Permission/authentication failures

## Summary

This comprehensive guide to anti-patterns and common mistakes provides:

### Critical Anti-Patterns (🚨 ABSOLUTELY FORBIDDEN)
1. **try-catch in Effect.gen** - Breaks Effect's error handling
2. **Type assertions** - Destroys type safety
3. **Missing return yield\*** - Causes unreachable code
4. **Effect.run\* inside effects** - Breaks composition
5. **Multiple Effect.provide** - Breaks memoization
6. **Manual fiber management** - Error-prone and verbose
7. **Ignoring defects** - Hides bugs
8. **Global state** - Breaks testability

### Performance Anti-Patterns
- No concurrency limits
- No caching strategy
- N+1 query problems
- No batching
- Excessive logging
- Memory leaks
- Resource exhaustion

### Architecture Anti-Patterns
- Monolithic services
- Circular dependencies
- God objects
- Tight coupling
- Leaking abstractions
- Missing error handling
- No layer composition

### Testing Anti-Patterns
- Using wrong testing framework
- Not using TestClock
- Flaky tests
- Testing implementation
- No mock layers
- Ignoring error paths
- No integration tests

**Key Principle**: Avoiding these anti-patterns leads to:
- Type-safe, maintainable code
- Performant, scalable applications
- Clean, testable architecture
- Reliable, deterministic tests

When in doubt, refer back to this guide to ensure you're following Effect-TS best practices and avoiding common pitfalls.
