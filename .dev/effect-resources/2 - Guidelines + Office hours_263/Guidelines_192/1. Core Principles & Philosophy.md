# 1. Core Principles & Philosophy

## Overview

Effect-TS represents a paradigm shift in TypeScript development, treating Effect not as a library but as a domain-specific language embedded in TypeScript for describing effectful computations. This section establishes the foundational principles that guide all Effect-TS development.

## 1.1 Functional Programming Foundations

### Purity (Within Effect Computations)

**Principle:** Effects are immutable, lazy descriptions of programs. Pure computations should be kept within Effect, with side effects explicitly represented in the type system.

**Core Concept:** An `Effect` is not the running program—it's a blueprint. Think of it as a recipe, not a cake. The recipe doesn't execute itself; it's a description that gets executed later by a Runtime.

```typescript
import { Effect } from "effect"

// ✅ GOOD: Pure computation wrapped in Effect
const calculateTotal = (items: Item[]): Effect.Effect<number> =>
  Effect.succeed(items.reduce((sum, item) => sum + item.price, 0))

// ✅ GOOD: Side effects are explicit in the type
const saveToDatabase = (data: Data): Effect.Effect<void, DatabaseError, Database> =>
  Effect.gen(function* () {
    const db = yield* Database
    yield* db.insert(data) // Side effect is tracked in type system
  })

// ❌ BAD: Hidden side effect, not tracked in types
const impureCalculation = (items: Item[]): number => {
  console.log("Calculating...") // Side effect!
  logToAnalytics(items) // Another hidden side effect!
  return items.reduce((sum, item) => sum + item.price, 0)
}

// ✅ GOOD: Side effects made explicit
const pureCalculation = (items: Item[]): Effect.Effect<number, never, Logger> =>
  Effect.gen(function* () {
    const logger = yield* Logger
    yield* logger.info("Calculating...")
    const total = items.reduce((sum, item) => sum + item.price, 0)
    return total
  })
```

**Rationale:**
- **Predictability:** Pure functions with same inputs always produce same outputs
- **Testability:** Pure logic is trivially testable without mocking
- **Composability:** Pure effects can be combined freely without fear of interference
- **Referential Transparency:** Effects can be assigned to variables and reused safely

**Mental Model:** Separation of "description" from "execution":

```typescript
// This DESCRIBES a program but doesn't execute it
const program = Effect.gen(function* () {
  yield* Effect.log("Starting")
  const result = yield* calculateTotal(items)
  yield* Effect.log("Completed")
  return result
})

// This line executes the description
Effect.runPromise(program) // Execution happens here!

// You can reuse the description safely
Effect.runPromise(program) // Separate execution
Effect.runPromise(program) // Another separate execution
```

### Immutability

**Principle:** Treat all data structures as immutable. Use Effect's `Data` module or immutable update patterns to create new versions instead of mutating existing data.

```typescript
import { Data, Effect } from "effect"

// ✅ GOOD: Immutable data structure using Data module
const user = Data.struct({
  id: "123",
  name: "Alice",
  email: "alice@example.com"
})

// Create updated version (original unchanged)
const updatedUser = Data.struct({
  ...user,
  email: "alice.new@example.com"
})

// ✅ GOOD: Immutable update in Effect
const updateUserEmail = (userId: string, newEmail: string) =>
  Effect.gen(function* () {
    const db = yield* Database
    const user = yield* db.users.findById(userId)
    
    // Create new user object instead of mutating
    const updated = { ...user, email: newEmail }
    
    yield* db.users.update(userId, updated)
    return updated
  })

// ❌ BAD: Mutable state
let globalState = { count: 0 }
const incrementMutable = () => {
  globalState.count++ // Mutation creates hidden coupling
  return globalState.count
}

// ✅ GOOD: Immutable state with Ref
const incrementImmutable = Effect.gen(function* () {
  const ref = yield* Ref.make({ count: 0 })
  
  yield* Ref.update(ref, (state) => ({
    count: state.count + 1 // Returns new state
  }))
  
  const state = yield* Ref.get(ref)
  return state.count
})
```

**Rationale:**
- **Predictability:** No action-at-a-distance through mutation
- **Concurrency Safety:** Immutable data is inherently thread-safe
- **Time Travel:** Previous states remain accessible for debugging
- **Optimizations:** Compiler can optimize based on immutability guarantees

**Array/Collection Updates:**

```typescript
import { Array as Arr } from "effect"

// ✅ GOOD: Functional array updates
const addItem = (items: ReadonlyArray<Item>, newItem: Item) =>
  [...items, newItem] // Creates new array

const removeItem = (items: ReadonlyArray<Item>, id: string) =>
  Arr.filter(items, item => item.id !== id) // Returns new array

const updateItem = (items: ReadonlyArray<Item>, id: string, updates: Partial<Item>) =>
  Arr.map(items, item =>
    item.id === id ? { ...item, ...updates } : item
  )

// ❌ BAD: Mutating arrays
const badAddItem = (items: Item[], newItem: Item) => {
  items.push(newItem) // Mutation!
  return items
}
```

### Composability

**Principle:** Build complex functionality by composing simple, focused pieces. Effect programs should be built from small, reusable effects that combine naturally.

```typescript
import { Effect, pipe } from "effect"

// ✅ GOOD: Small, focused functions that compose
const validateEmail = (email: string): Effect.Effect<string, ValidationError> =>
  email.includes("@")
    ? Effect.succeed(email)
    : Effect.fail(new ValidationError({ field: "email" }))

const checkEmailUnique = (email: string): Effect.Effect<string, DatabaseError, Database> =>
  Effect.gen(function* () {
    const db = yield* Database
    const exists = yield* db.users.existsByEmail(email)
    if (exists) {
      return yield* Effect.fail(new DatabaseError({ message: "Email already exists" }))
    }
    return email
  })

const normalizeEmail = (email: string): Effect.Effect<string> =>
  Effect.succeed(email.toLowerCase().trim())

// Compose into larger operation
const processEmail = (email: string) =>
  pipe(
    email,
    normalizeEmail,
    Effect.flatMap(validateEmail),
    Effect.flatMap(checkEmailUnique)
  )

// Or using Effect.gen for readability
const processEmailGen = (email: string) =>
  Effect.gen(function* () {
    const normalized = yield* normalizeEmail(email)
    const validated = yield* validateEmail(normalized)
    const unique = yield* checkEmailUnique(validated)
    return unique
  })
```

**Function Composition Patterns:**

```typescript
// Sequential composition (pipeline)
const processOrder = (order: Order) =>
  pipe(
    order,
    validateOrder,
    Effect.flatMap(calculateTotals),
    Effect.flatMap(applyDiscounts),
    Effect.flatMap(processPayment)
  )

// Parallel composition
const getUserData = (userId: string) =>
  Effect.all({
    user: getUser(userId),
    posts: getUserPosts(userId),
    stats: getUserStats(userId)
  }, { concurrency: "unbounded" })

// Conditional composition
const processPayment = (method: PaymentMethod) =>
  Effect.gen(function* () {
    if (method === "credit_card") {
      return yield* processCreditCard()
    } else if (method === "paypal") {
      return yield* processPayPal()
    } else {
      return yield* processBankTransfer()
    }
  })
```

**Rationale:**
- **Maintainability:** Small functions are easier to understand and modify
- **Reusability:** Focused functions can be reused in different contexts
- **Testability:** Each piece can be tested in isolation
- **Flexibility:** Easy to rearrange or replace individual pieces

### Type Safety

**Principle:** Leverage TypeScript's type system to catch errors at compile time. Effect's type signature `Effect<A, E, R>` captures success type, error type, and requirements.

```typescript
// Effect signature tells the complete story:
// Effect<A, E, R>
//        │  │  └─ Requirements: What this effect needs to run
//        │  └──── Errors: How this can fail (typed!)
//        └─────── Success: What this produces on success

// ✅ GOOD: Complete type information
const getUser = (id: string): Effect.Effect
  User,              // Success: returns User
  UserNotFoundError, // Error: can fail with UserNotFoundError
  Database           // Requirements: needs Database service
> =>
  Effect.gen(function* () {
    const db = yield* Database
    const user = yield* db.users.findById(id)
    if (!user) {
      return yield* Effect.fail(new UserNotFoundError({ id }))
    }
    return user
  })

// The type system enforces error handling
const program = Effect.gen(function* () {
  // TypeScript knows this can fail with UserNotFoundError
  const user = yield* getUser("123")
  
  // Must handle or propagate the error
  return user
}).pipe(
  Effect.catchTag("UserNotFoundError", (error) =>
    Effect.succeed(defaultUser) // Or handle it
  )
)

// ❌ BAD: Type system can't help with thrown errors
const unsafeGetUser = async (id: string): Promise<User> => {
  const user = await db.findById(id)
  if (!user) {
    throw new Error("Not found") // Lost in type system!
  }
  return user
}
```

**Type Inference Benefits:**

```typescript
// Effect's type inference is powerful - let it work!
const program = Effect.gen(function* () {
  // TypeScript infers result is Effect<User, UserNotFoundError, Database>
  const user = yield* getUser("123")
  
  // Infers posts is Effect<Post[], FetchError, ApiClient>
  const posts = yield* getPosts(user.id)
  
  // Combined type: Effect
  //   { user: User, posts: Post[] },
  //   UserNotFoundError | FetchError,
  //   Database | ApiClient
  // >
  return { user, posts }
})
```

**Compile-Time Safety:**

```typescript
// TypeScript prevents mixing incompatible types
const userId: UserId = "raw-string" // ❌ Compile error with branded types

// Correct usage with validation
const userId = yield* Schema.decode(UserId)("raw-string") // ✅ Runtime validation

// Type system prevents forgetting dependencies
const program = Effect.gen(function* () {
  const user = yield* getUser("123") // Requires Database
  return user
})

// Must provide Database before running
Effect.runPromise(program) // ❌ Compile error: Database not provided
Effect.runPromise(program.pipe(Effect.provide(DatabaseLive))) // ✅ Correct
```

**Rationale:**
- **Early Detection:** Catch errors at compile time, not runtime
- **Documentation:** Types serve as always-up-to-date documentation
- **Refactoring Safety:** Type system catches breaking changes
- **IDE Support:** Rich autocompletion and inline documentation

### Explicit Error Handling

**Principle:** All potential failures MUST be represented in the Effect's error channel (`E`). The type system forces you to acknowledge every possible failure mode.

```typescript
import { Data, Effect } from "effect"

// Define specific error types
class UserNotFoundError extends Data.TaggedError("UserNotFoundError")<{
  userId: string
}> {}

class DatabaseError extends Data.TaggedError("DatabaseError")<{
  cause: unknown
  operation: string
}> {}

class ValidationError extends Data.TaggedError("ValidationError")<{
  field: string
  message: string
}> {}

// ✅ GOOD: All errors in the type signature
const getUserProfile = (id: string): Effect.Effect
  UserProfile,
  UserNotFoundError | DatabaseError | ValidationError,
  Database | Cache
> =>
  Effect.gen(function* () {
    const db = yield* Database
    const cache = yield* Cache
    
    // Validate input
    if (!id || id.length === 0) {
      return yield* Effect.fail(
        new ValidationError({ field: "id", message: "ID cannot be empty" })
      )
    }
    
    // Try cache first
    const cached = yield* cache.get(id).pipe(Effect.option)
    if (cached._tag === "Some") return cached.value
    
    // Fetch from database
    const user = yield* db.users.findById(id).pipe(
      Effect.mapError(cause => new DatabaseError({ cause, operation: "findById" }))
    )
    
    if (!user) {
      return yield* Effect.fail(new UserNotFoundError({ userId: id }))
    }
    
    return user
  })

// Caller MUST handle errors or let them propagate
const program = getUserProfile("123").pipe(
  Effect.catchTags({
    UserNotFoundError: (error) =>
      Effect.succeed(defaultProfile),
    DatabaseError: (error) =>
      Effect.fail(new ServiceUnavailableError({ cause: error })),
    ValidationError: (error) =>
      Effect.fail(new BadRequestError({ cause: error }))
  })
)
```

**Railway-Oriented Programming:**

```typescript
// Errors flow automatically through the railway
const processUser = (id: string) =>
  Effect.gen(function* () {
    // If this fails, entire chain short-circuits
    const user = yield* getUser(id)
    
    // Only runs if getUser succeeds
    const validated = yield* validateUser(user)
    
    // Only runs if validation succeeds
    const enriched = yield* enrichUserData(validated)
    
    // Only runs if enrichment succeeds
    return yield* saveUser(enriched)
  }) // All errors automatically propagate

// No need for try-catch at each step!
```

**Defects vs Typed Errors:**

```typescript
// Typed errors: Recoverable, expected failures
const parseUserInput = (input: unknown): Effect.Effect<User, ValidationError> =>
  Schema.decodeUnknown(UserSchema)(input).pipe(
    Effect.mapError(cause => new ValidationError({ cause }))
  )

// Defects: Unrecoverable, unexpected failures (bugs)
const parseConfig = (config: unknown): Effect.Effect<Config> =>
  Schema.decodeUnknown(ConfigSchema)(config).pipe(
    Effect.catchTag("ParseError", (error) =>
      Effect.die(error) // This is a bug, not recoverable
    )
  )
```

**Rationale:**
- **Exhaustiveness:** Type system ensures all error cases are handled
- **Documentation:** Error types document all possible failures
- **Safe Refactoring:** Adding new error types causes compile errors at call sites
- **No Hidden Failures:** Every failure mode is explicit and visible

## 1.2 Effect-First Development

### No Plain Promises/async-await

**Principle:** All asynchronous operations MUST use Effect, not Promises or async/await. This provides better composition, error handling, and type safety.

```typescript
// ❌ BAD: Promise-based code loses type safety
async function fetchUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${id}`)
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`) // Type information lost!
  }
  return response.json()
}

// ✅ GOOD: Effect-based with full type safety
const fetchUser = (id: string): Effect.Effect<User, FetchError | ParseError> =>
  Effect.gen(function* () {
    const response = yield* Effect.tryPromise({
      try: () => fetch(`/api/users/${id}`),
      catch: (error) => new FetchError({ cause: error })
    })
    
    if (!response.ok) {
      return yield* Effect.fail(
        new FetchError({ statusCode: response.status })
      )
    }
    
    const data = yield* Effect.tryPromise({
      try: () => response.json(),
      catch: (error) => new ParseError({ cause: error })
    })
    
    return yield* Schema.decodeUnknown(UserSchema)(data)
  })
```

**Converting Promises to Effects:**

```typescript
// Simple promise conversion
const simpleConversion = Effect.promise(() => fetch("/api/data"))

// Promise with error handling
const withErrorHandling = Effect.tryPromise({
  try: () => fetch("/api/data"),
  catch: (error) => new NetworkError({ cause: error })
})

// Promise with resource cleanup
const withCleanup = Effect.acquireRelease(
  Effect.tryPromise({
    try: () => openConnection(),
    catch: (error) => new ConnectionError({ cause: error })
  }),
  (conn) => Effect.sync(() => conn.close())
)
```

**Why Effect Over Promise:**

| Feature | Promise | Effect |
|---------|---------|--------|
| **Typed Errors** | ❌ Throws are untyped | ✅ Error channel is typed |
| **Cancellation** | ❌ Not cancellable | ✅ Interruptible by default |
| **Resource Safety** | ❌ Manual cleanup | ✅ Automatic with acquireRelease |
| **Composition** | ❌ Promise.all limited | ✅ Rich combinators |
| **Laziness** | ❌ Eager execution | ✅ Lazy, reusable blueprints |
| **Dependencies** | ❌ Global or passed manually | ✅ Tracked in type system |
| **Retries** | ❌ Manual implementation | ✅ Built-in with schedules |
| **Timeouts** | ❌ Race with setTimeout | ✅ Built-in Effect.timeout |

**Rationale:**
- **Type Safety:** Errors are typed and tracked
- **Composability:** Effects compose better than Promises
- **Resource Management:** Automatic cleanup with interruption
- **Testability:** Easy to mock and test without actual I/O

### Declarative Blueprints vs Execution

**Principle:** Effects are descriptions (blueprints), not executions. They only run when explicitly executed by a Runtime. This enables powerful composition and reuse patterns.

```typescript
// This CREATES a blueprint, but doesn't execute it
const fetchUserBlueprint = Effect.gen(function* () {
  yield* Effect.log("Fetching user...")
  const response = yield* Effect.tryPromise({
    try: () => fetch("/api/user"),
    catch: (e) => new NetworkError({ cause: e })
  })
  yield* Effect.log("User fetched!")
  return response
})

// Nothing has happened yet! No logs, no network calls.

// You can reuse the blueprint
const program1 = fetchUserBlueprint // Same blueprint
const program2 = fetchUserBlueprint // Same blueprint

// Execution happens when you run it
Effect.runPromise(program1) // NOW it executes (once)
Effect.runPromise(program2) // Separate execution (again)

// ❌ BAD: Promise executes immediately
const promise = (async () => {
  console.log("Fetching...") // Logs immediately!
  return await fetch("/api/user") // Fetches immediately!
})() // Already running!

// Can't prevent execution or reuse this safely
```

**Blueprint Composition:**

```typescript
// Build complex programs from simple blueprints
const step1 = Effect.log("Step 1")
const step2 = Effect.log("Step 2")
const step3 = Effect.log("Step 3")

// Compose into larger blueprint
const workflow = Effect.gen(function* () {
  yield* step1
  yield* step2
  yield* step3
})

// Still just a blueprint! Can be composed further
const fullProgram = Effect.gen(function* () {
  yield* Effect.log("Starting...")
  yield* workflow // Reuse composed workflow
  yield* Effect.log("Done!")
})

// Only executes when explicitly run
Effect.runPromise(fullProgram)
```

**Lazy Evaluation Benefits:**

```typescript
// Build programs conditionally without execution
const makeProgram = (useCache: boolean) =>
  Effect.gen(function* () {
    if (useCache) {
      return yield* fetchFromCache() // Blueprint, not execution
    } else {
      return yield* fetchFromDatabase() // Blueprint, not execution
    }
  })

// Decide at runtime which path to take
const program = makeProgram(config.cacheEnabled)

// Nothing has executed until now:
Effect.runPromise(program)
```

**Rationale:**
- **Reusability:** Blueprints can be reused safely across multiple executions
- **Composition:** Combine blueprints without triggering execution
- **Testing:** Test blueprints without actual side effects
- **Optimization:** Runtime can optimize execution strategy

### Holistic Thinking: Effect<A, E, R>

**Principle:** Always think in terms of the complete Effect signature: Success (`A`), Errors (`E`), and Requirements (`R`). This forces complete consideration of all aspects.

```typescript
// Complete thinking about an operation:
const createUser = (data: NewUser): Effect.Effect
  User,              // A: What does this produce on success?
  | ValidationError  // E: How can this fail?
  | DatabaseError    //    (List ALL possible errors)
  | DuplicateError,  //    
  Database           // R: What does this need to run?
  | Logger           //    (List ALL dependencies)
  | EmailService     //
> =>
  Effect.gen(function* () {
    // Access ALL requirements explicitly
    const db = yield* Database
    const logger = yield* Logger
    const email = yield* EmailService
    
    // Handle ALL error cases
    const validated = yield* validateUser(data) // ValidationError
    const exists = yield* checkDuplicate(validated.email) // DatabaseError
    if (exists) {
      return yield* Effect.fail(new DuplicateError({ email: validated.email }))
    }
    
    const user = yield* db.users.create(validated) // DatabaseError
    yield* logger.info("User created", { userId: user.id })
    yield* email.sendWelcome(user.email) // EmailError (handled internally)
    
    return user // Success case
  })
```

**The Effect Mental Model:**

```
         ┌─────────────────────────────────────┐
         │   Effect<A, E, R>                  │
         │                                     │
         │   Blueprint/Program Description     │
         └─────────────────────────────────────┘
                        │
                        │ When executed by Runtime:
                        ↓
         ┌──────────────┬──────────────┬──────────────┐
         │              │              │              │
         ↓              ↓              ↓              ↓
    Success(A)    Failure(E)    Defect         Interruption
         │              │              │              │
         │              │              │              │
    Return value   Typed error   Bug/Panic     Cancelled
```

**Complete Type-Level Documentation:**

```typescript
// The signature tells you EVERYTHING
interface UserService {
  readonly getUser: (id: string) => Effect.Effect
    User,                    // Returns User on success
    UserNotFoundError,       // Can fail if user doesn't exist
    Database                 // Needs Database to run
  >
  
  readonly createUser: (data: NewUser) => Effect.Effect
    User,                    // Returns created User
    ValidationError          // Can fail validation
    | DatabaseError          // Can fail database operation
    | DuplicateError,        // Can fail if duplicate email
    Database                 // Needs Database
    | Logger                 // Needs Logger
    | EmailService           // Needs EmailService
  >
}

// Caller knows exactly what to handle and provide
const program = Effect.gen(function* () {
  const service = yield* UserService
  
  // Type system knows all possible errors
  const user = yield* service.createUser(newUser)
  
  return user
}).pipe(
  // Must handle all error types
  Effect.catchTags({
    ValidationError: handleValidation,
    DatabaseError: handleDatabase,
    DuplicateError: handleDuplicate
  }),
  // Must provide all requirements
  Effect.provide(AppLayer) // Contains Database + Logger + EmailService
)
```

**Rationale:**
- **Completeness:** Forces consideration of all aspects
- **Documentation:** Signature documents behavior completely
- **Safety:** Can't forget to handle errors or provide dependencies
- **Refactoring:** Changes to signature surface at all call sites

## 1.3 Design Philosophy

### Make Impossible States Unrepresentable

**Principle:** Use the type system to prevent invalid states from being constructed. If it compiles, it's valid.

```typescript
import { Schema } from "@effect/schema"

// ❌ BAD: Can represent invalid states
interface User {
  id: string // Could be empty
  email: string // Could be invalid format
  age: number // Could be negative
  status: string // Could be any string
}

// ✅ GOOD: Invalid states are impossible
const UserId = Schema.String.pipe(
  Schema.brand("UserId"),
  Schema.minLength(1)
)

const Email = Schema.String.pipe(
  Schema.pattern(/^[^\s@]+@[^\s@]+\.[^\s@]+$/),
  Schema.brand("Email")
)

const Age = Schema.Number.pipe(
  Schema.int(),
  Schema.greaterThanOrEqualTo(0),
  Schema.lessThanOrEqualTo(150)
)

const UserStatus = Schema.Literal("active", "inactive", "suspended")

const User = Schema.Struct({
  id: UserId,
  email: Email,
  age: Age,
  status: UserStatus
})

// Can't create invalid user - compile error!
const invalid = { id: "", email: "bad", age: -5, status: "unknown" } // ❌
const valid = yield* Schema.decode(User)(validData) // ✅ Validated
```

**Branded Types for Domain Concepts:**

```typescript
// Create nominal types that can't be mixed
const OrderId = Schema.String.pipe(Schema.brand("OrderId"))
const ProductId = Schema.String.pipe(Schema.brand("ProductId"))
const UserId = Schema.String.pipe(Schema.brand("UserId"))

type OrderId = Schema.Schema.Type<typeof OrderId>
type ProductId = Schema.Schema.Type<typeof ProductId>
type UserId = Schema.Schema.Type<typeof UserId>

// Can't accidentally mix IDs
const getOrder = (id: OrderId) => { /* ... */ }
const productId: ProductId = /* ... */

getOrder(productId) // ❌ Compile error: ProductId is not OrderId
```

**State Machines with Discriminated Unions:**

```typescript
// ❌ BAD: Can represent inconsistent states
interface Order {
  status: "pending" | "shipped" | "delivered"
  shippingDate?: Date  // Only valid if shipped
  trackingNumber?: string  // Only valid if shipped
  deliveryDate?: Date  // Only valid if delivered
}

// Can create invalid order: status="pending" but has trackingNumber
const invalid: Order = {
  status: "pending",
  trackingNumber: "ABC123" // Shouldn't be here!
}

// ✅ GOOD: Each state has only valid fields
type Order =
  | { status: "pending" }
  | { status: "shipped"; shippingDate: Date; trackingNumber: string }
  | { status: "delivered"; shippingDate: Date; trackingNumber: string; deliveryDate: Date }

// Can only create valid orders
const pending: Order = { status: "pending" }
const shipped: Order = {
  status: "shipped",
  shippingDate: new Date(),
  trackingNumber: "ABC123"
}

// Invalid state is impossible to construct
const invalid: Order = {
  status: "pending",
  trackingNumber: "ABC123" // ❌ Compile error!
}
```

**Rationale:**
- **Correctness:** Invalid states literally cannot exist
- **Maintainability:** Compiler catches inconsistencies
- **Documentation:** Types document valid states
- **Refactoring Safety:** Changes to state model cause compile errors

### Composition Over Inheritance

**Principle:** Build complex functionality by composing simple, independent pieces. Avoid deep inheritance hierarchies. Use Layer composition for services.

```typescript
// ❌ BAD: Deep inheritance hierarchy
class BaseRepository {
  async findById(id: string) { /* ... */ }
}

class UserRepository extends BaseRepository {
  async findByEmail(email: string) { /* ... */ }
}

class AdminUserRepository extends UserRepository {
  async findAdmins() { /* ... */ }
}

// ✅ GOOD: Composition with services
class UserRepository extends Effect.Service<UserRepository>()(
  "UserRepository",
  {
    effect: Effect.gen(function* () {
      const db = yield* Database
      
      return {
        findById: (id: string) => db.query("SELECT * FROM users WHERE id = ?", [id]),
        findByEmail: (email: string) => db.query("SELECT * FROM users WHERE email = ?", [email])
      }
    }),
    dependencies: [Database.Default]
  }
) {}

class AdminService extends Effect.Service<AdminService>()(
  "AdminService",
  {
    effect: Effect.gen(function* () {
      const users = yield* UserRepository // Compose, don't inherit
      const permissions = yield* PermissionService // Compose multiple services
      
      return {
        findAdmins: () => Effect.gen(function* () {
          const allUsers = yield* users.findAll()
          const admins = yield* Effect.filter(
            allUsers,
            user => permissions.isAdmin(user.id)
          )
          return admins
        })
      }
    }),
    dependencies: [UserRepository.Default, PermissionService.Default]
  }
) {}
```

**Mixin Pattern for Shared Behavior:**

```typescript
// Reusable behaviors as functions, not base classes
const withCaching = <A, E, R>(
  operation: Effect.Effect<A, E, R>,
  key: string
): Effect.Effect<A, E, R | Cache> =>
  Effect.gen(function* () {
    const cache = yield* Cache
    
    const cached = yield* cache.get(key).pipe(Effect.option)
    if (cached._tag === "Some") return cached.value
    
    const result = yield* operation
    yield* cache.set(key, result)
    return result
  })

const withLogging = <A, E, R>(
  operation: Effect.Effect<A, E, R>,
  message: string
): Effect.Effect<A, E, R | Logger> =>
  Effect.gen(function* () {
    const logger = yield* Logger
    yield* logger.info(message)
    const result = yield* operation
    yield* logger.info(`${message} completed`)
    return result
  })

// Compose behaviors
const getUserWithBehaviors = (id: string) =>
  pipe(
    getUserCore(id),
    withCaching(`user:${id}`),
    withLogging(`Fetching user ${id}`)
  )
```

**Rationale:**
- **Flexibility:** Easy to add/remove/replace components
- **Testability:** Test individual pieces in isolation
- **Reusability:** Share behaviors without inheritance
- **Maintainability:** Changes don't ripple through hierarchies

### Separate "What" from "How"

**Principle:** Business logic (what to do) should be separate from execution details (how to do it). Configuration and strategies should be externalized.

```typescript
// ❌ BAD: Business logic mixed with execution details
const processOrder = async (order: Order) => {
  // Business logic mixed with implementation
  const retries = 3
  const backoff = 1000
  
  for (let i = 0; i < retries; i++) {
    try {
      await fetch("/api/payment", {
        method: "POST",
        body: JSON.stringify(order)
      })
      return
    } catch (error) {
      if (i === retries - 1) throw error
      await new Promise(resolve => setTimeout(resolve, backoff * (i + 1)))
    }
  }
}

// ✅ GOOD: Business logic separated from execution
const processOrder = (order: Order): Effect.Effect<void, PaymentError, PaymentService> =>
  Effect.gen(function* () {
    const payment = yield* PaymentService
    yield* payment.charge(order) // What to do
  }) // How it's done (retries, etc.) is in the service/layer

// Configuration separate from logic
const PaymentServiceLive = Layer.effect(
  PaymentService,
  Effect.gen(function* () {
    const config = yield* Config
    const http = yield* HttpClient
    
    const charge = (order: Order) =>
      http.post("/api/payment", { body: order }).pipe(
        // "How" is configured separately
        Effect.retry({
          times: config.payment.retries,
          schedule: Schedule.exponential(config.payment.backoff)
        })
      )
    
    return { charge }
  })
)
```

**Declarative Configuration:**

```typescript
// Define WHAT operations do

  fetchUser: (id: string) => database.users.findById(id),
  updateUser: (id: string, data: Partial<User>) => database.users.update(id, data),
```

**Strategy Pattern with Effect:**

```typescript
// Define interface for strategy (what)
interface CachingStrategy {
  get: (key: string) => Effect.Effect<Option<unknown>>
  set: (key: string, value: unknown) => Effect.Effect<void>
}

// Different strategies (how)
const memoryCachingStrategy: CachingStrategy = {
  get: (key) => Effect.sync(() => memoryCache.get(key)),
  set: (key, value) => Effect.sync(() => memoryCache.set(key, value))
}

const redisCachingStrategy: CachingStrategy = {
  get: (key) => Effect.tryPromise(() => redis.get(key)),
  set: (key, value) => Effect.tryPromise(() => redis.set(key, value))
}

// Business logic uses strategy (what) without knowing how
const makeService = (strategy: CachingStrategy) =>
  Effect.gen(function* () {
    return {
      getData: (key: string) => Effect.gen(function* () {
        const cached = yield* strategy.get(key)
        if (Option.isSome(cached)) return cached.value
        
        const data = yield* fetchFromDatabase(key)
        yield* strategy.set(key, data)
        return data
      })
    }
  })
```

**Rationale:**
- **Testability:** Test business logic without execution concerns
- **Flexibility:** Change execution strategies without changing logic
- **Configuration:** Adjust behavior through configuration, not code changes
- **Clarity:** Business rules are clear and uncluttered

## Summary

These core principles form the foundation of Effect-TS development:

**Functional Programming Foundations:**
- **Purity:** Effects are immutable descriptions executed by Runtime
- **Immutability:** Use immutable data structures and functional updates
- **Composability:** Build complex from simple, focused pieces
- **Type Safety:** Leverage `Effect<A, E, R>` for complete type information
- **Explicit Error Handling:** All failures in typed error channel

**Effect-First Development:**
- **No Promises:** Use Effect for all async operations
- **Declarative Blueprints:** Effects describe, Runtime executes
- **Holistic Thinking:** Consider success, errors, and requirements together

**Design Philosophy:**
- **Impossible States:** Use types to prevent invalid data
- **Composition Over Inheritance:** Compose services, avoid hierarchies
- **Separate What from How:** Business logic separate from execution

These principles work together to create robust, maintainable, and type-safe applications. Every pattern and practice in Effect-TS derives from and reinforces these core foundations.
