## 2. Syntax & Language Patterns

### 2.1 Effect.gen vs Effect.fn vs .pipe

#### Core Principle: The Hybrid Pattern

The fundamental approach to Effect-TS composition is the **Hybrid Pattern**: use `Effect.gen` or `Effect.fn` for business logic and core sequential operations, and use `.pipe` for post-processing, error handling, and composition.

#### Effect.gen Usage

**When to use Effect.gen:**

1. **Business logic sequences** - Multiple dependent operations that need previous results
2. **Complex control flow** - Conditionals, loops, branching logic
3. **Service dependency access** - When you need to access multiple services
4. **Resource management** - Managing dependencies and cleanup
5. **Function factories** - Building functions with dependencies

**Effect.gen Syntax:**

```typescript
import { Effect } from "effect"

// ✅ PREFERRED: Complex business logic with multiple steps
const createUser = (user: NewUser) =>
  Effect.gen(function* () {
    // Access dependencies
    const db = yield* Database
    const logger = yield* Logger
    
    // Sequential operations with intermediate results
    const validated = yield* validateUser(user)
    const hashedPassword = yield* hashPassword(validated.password)
    const userData = { ...validated, password: hashedPassword }
    
    // Conditional logic
    if (yield* db.users.exists(userData.email)) {
      return yield* Effect.fail(new UserExistsError({ email: userData.email }))
    }
    
    // Create and return
    const created = yield* db.users.create(userData)
    yield* logger.info("User created", { userId: created.id })
    
    return created
  })
```

**Generator Function Semantics:**

- Use `yield*` to run another Effect (the `*` is mandatory)
- Use `return yield*` for terminal effects (`Effect.fail`, `Effect.die`, `Effect.interrupt`)
- Return values directly for success cases
- Variables can reference previous yields

**Type Inference in Generators:**

Effect.gen provides excellent type inference. The TypeScript compiler automatically infers types through the generator, reducing the need for explicit annotations:

```typescript
const program = Effect.gen(function* () {
  const user = yield* getUser("123")  // Type inferred: User
  const posts = yield* getPosts(user.id)  // Type inferred: Post[]
  const enriched = posts.map(post => ({ ...post, author: user.name }))  // Type inferred automatically
  return enriched
})
```

#### Effect.fn Usage

**When to use Effect.fn:**

Effect.fn is the preferred pattern for creating reusable Effect-returning functions. It combines the readability of Effect.gen with automatic observability benefits.

**Key Benefits:**

1. **Automatic span creation** - Creates a tracing span with the function name
2. **Named functions for tracing** - Shows up clearly in distributed traces
3. **Function factories** - Perfect for building reusable Effect functions
4. **Observability benefits** - Built-in tracing without extra code

**Effect.fn Syntax:**

```typescript
import { Effect } from "effect"

// ✅ PREFERRED: Named function with automatic tracing
const calculateDiscount = Effect.fn("calculateDiscount")(
  function* (price: number, discount: number) {
    // Automatic span created with name "calculateDiscount"
    
    if (discount < 0 || discount > 100) {
      return yield* Effect.fail(new InvalidDiscountError({ discount }))
    }
    
    const discountAmount = (price * discount) / 100
    const finalPrice = price - discountAmount
    
    return finalPrice
  },
  // Optional: Add pipe operations as additional arguments
  Effect.annotateLogs({ operation: "discount-calculation" }),
  // Can also access function arguments
  (effect, price, discount) => 
    Effect.annotateLogs(effect, { price, discount })
)

// Usage
const result = yield* calculateDiscount(100, 15)  // Traced as "calculateDiscount"

// ✅ Without span name (when you don't need tracing)
const withNoSpan = Effect.fn(function* (x: number, y: number) {
  yield* Effect.log("Calculating sum", { x, y })
  return x + y
})
```

**Effect.fn vs Effect.gen:**

- Use `Effect.fn` when creating **reusable functions** that return Effects
- Use `Effect.gen` when creating **one-off Effect programs** or anonymous generators
- Effect.fn provides better observability out-of-the-box
- Effect.fn supports pipe operations as additional function arguments

#### .pipe Usage

**When to use .pipe:**

1. **Post-processing** - Transforming results after core logic
2. **Error handling transformations** - `catchTag`, `catchAll`, `mapError`
3. **Single-step transformations** - Simple `map`, `flatMap`, `tap` operations
4. **Layer composition** - Building dependency graphs
5. **Middleware patterns** - Adding cross-cutting concerns
6. **Tracing and logging** - Adding observability

**Pipe Composition Patterns:**

```typescript
import { Effect, Layer } from "effect"

// ✅ PREFERRED: Post-processing and error handling
const getUser = (id: string) =>
  Effect.gen(function* () {
    const db = yield* Database
    const user = yield* db.users.findById(id)
    
    if (!user) {
      return yield* Effect.fail(new UserNotFoundError({ id }))
    }
    
    return user
  }).pipe(
    // Error transformation
    Effect.catchTag("DatabaseError", (error) =>
      Effect.fail(new ServiceUnavailableError({ cause: error }))
    ),
    // Add tracing
    Effect.withSpan("user.get", {
      attributes: { "user.id": id }
    }),
    // Add logging
    Effect.tap((user) => Effect.log("User retrieved", { userId: user.id })),
    Effect.tapError((error) => Effect.logError("Failed to get user", { error }))
  )

// ✅ PREFERRED: Layer composition
const AppLayer = Layer.empty.pipe(
  Layer.provide(DatabaseLive),
  Layer.provide(LoggerLive),
  Layer.provideMerge(CacheLive),
  Layer.provideMerge(UserServiceLive)
)

// ✅ PREFERRED: Simple transformations
const activeUserNames = getActiveUsers().pipe(
  Effect.map(users => users.map(user => user.name)),
  Effect.map(names => names.sort())
)
```

**Function-First vs Value-First:**

Effect-TS uses **function-first** style in pipes:

```typescript
// ✅ CORRECT: Function-first (Effect style)
const result = pipe(
  Effect.succeed([1, 2, 3, 4, 5]),
  Effect.map(arr => arr.filter(n => n % 2 === 0)),
  Effect.map(arr => arr.map(n => n * 2))
)

// ❌ AVOID: Value-first (older style)
const result = pipe(
  [1, 2, 3, 4, 5],
  Array.filter(n => n % 2 === 0),
  Array.map(n => n * 2)
)
```

#### The Hybrid Pattern in Practice

**✅ CORRECT: Combining Effect.gen and .pipe**

```typescript
const processOrder = (order: Order) =>
  Effect.gen(function* () {
    // Core business logic with Effect.gen
    const validated = yield* validateOrder(order)
    const calculated = yield* calculateTotals(validated)
    const discounted = yield* applyDiscounts(calculated)
    const paid = yield* processPayment(discounted)
    const updated = yield* updateInventory(paid)
    const confirmed = yield* sendConfirmation(updated)
    
    return confirmed
  }).pipe(
    // Post-processing with .pipe
    Effect.catchTag("PaymentError", handlePaymentFailure),
    Effect.catchTag("InventoryError", handleInventoryFailure),
    Effect.withSpan("order.process", {
      attributes: { "order.id": order.id }
    }),
    Effect.retry({
      times: 3,
      schedule: Schedule.exponential("1 second")
    })
  )
```

#### Anti-Patterns to Avoid

**❌ BAD: Using .pipe for Complex Sequential Logic**

```typescript
// ❌ WRONG: Hard to read and maintain
const processOrder = (order: Order) =>
  Effect.succeed(order).pipe(
    Effect.flatMap((order) => validateOrder(order)),
    Effect.flatMap((validated) => calculateTotals(validated)),
    Effect.flatMap((calculated) => applyDiscounts(calculated)),
    Effect.flatMap((discounted) => processPayment(discounted)),
    Effect.flatMap((paid) => updateInventory(paid)),
    Effect.flatMap((updated) => sendConfirmation(updated))
  )

// ✅ GOOD: Clear and maintainable with Effect.gen
const processOrder = (order: Order) =>
  Effect.gen(function* () {
    const validated = yield* validateOrder(order)
    const calculated = yield* calculateTotals(validated)
    const discounted = yield* applyDiscounts(calculated)
    const paid = yield* processPayment(discounted)
    const updated = yield* updateInventory(paid)
    return yield* sendConfirmation(updated)
  })
```

**❌ BAD: Using Effect.gen for Simple Transformations**

```typescript
// ❌ WRONG: Unnecessary complexity
const formatUserNames = Effect.gen(function* () {
  const users = yield* getUsers()
  return users.map(user => user.name.toUpperCase())
})

// ✅ GOOD: Simple and direct with .pipe
const formatUserNames = getUsers().pipe(
  Effect.map(users => users.map(user => user.name.toUpperCase()))
)
```

#### Decision Matrix

| Context | Syntax Choice | Reasoning |
|---------|---------------|-----------|
| **Business Logic** | Effect.gen/Effect.fn | Multiple steps, dependencies, conditional logic |
| **Reusable Functions** | Effect.fn | Named tracing, observability, function factories |
| **Error Handling** | .pipe | Composable error transformations |
| **Layer Building** | .pipe | Dependency composition patterns |
| **Single Transforms** | .pipe | Simple, functional transformations |
| **Resource Management** | Effect.gen | Managing dependencies and cleanup |
| **Post-Processing** | .pipe | Adding tracing, caching, metadata |
| **Control Flow** | Effect.gen | Conditionals, loops, complex branching |
| **Service Methods** | Effect.gen/Effect.fn | Building service interfaces with dependencies |

#### Refactoring Between Styles

When refactoring code, apply these rules:

**Rule 1: Complex .pipe chains → Effect.gen**

If you have more than 3 sequential `.flatMap` calls, refactor to Effect.gen:

```typescript
// BEFORE: Hard to follow
const process = input.pipe(
  Effect.flatMap(step1),
  Effect.flatMap(step2),
  Effect.flatMap(step3),
  Effect.flatMap(step4)
)

// AFTER: Clear and maintainable
const process = Effect.gen(function* () {
  const result1 = yield* step1(input)
  const result2 = yield* step2(result1)
  const result3 = yield* step3(result2)
  return yield* step4(result3)
})
```

**Rule 2: Anonymous Effect.gen → Effect.fn**

If you're creating a reusable function, use Effect.fn instead of Effect.gen:

```typescript
// BEFORE: Anonymous generator
const calculateTotal = (items: Item[]) =>
  Effect.gen(function* () {
    // logic
  })

// AFTER: Named, traceable function
const calculateTotal = Effect.fn("calculateTotal")(
  function* (items: Item[]) {
    // same logic
  }
)
```

### 2.2 Module Import Conventions

#### Single-Character Imports for Common Modules

Effect-TS uses single-character aliases for frequently used modules to reduce verbosity while maintaining clarity:

**Standard Single-Character Aliases:**

```typescript
import * as S from "@effect/schema/Schema"  // Schema
import * as A from "effect/Array"           // Array (alternative: Arr)
import * as O from "effect/Option"          // Option
import * as E from "effect/Either"          // Either
import * as F from "effect/Function"        // Function (alternative: Fn)
```

**All Other Modules Use Full Names:**

```typescript
import * as Effect from "effect/Effect"
import * as Layer from "effect/Layer"
import * as Context from "effect/Context"
import * as Data from "effect/Data"
import * as Ref from "effect/Ref"
import * as Stream from "effect/Stream"
import * as Queue from "effect/Queue"
import { pipe } from "effect"
```

#### Alternative Alias Standardization

When using descriptive aliases instead of single characters, use these standard forms:

```typescript
// Standard descriptive aliases
import { Array as Arr } from "effect"
import { Function as Fn } from "effect"
import { Schema as S } from "@effect/schema"
```

**Refactoring Rules:**

When refactoring from single-letter to descriptive aliases:
- `A.` → `Arr.` (all references must be updated)
- `F.` → `Fn.` (all references must be updated)
- Update ALL usage throughout the file consistently

#### Import Organization

Organize imports in this order for consistency:

```typescript
// 1. Effect core modules
import { Effect, Layer, Context, Data } from "effect"
import { pipe } from "effect"

// 2. Effect data structures
import * as Array from "effect/Array"
import * as Option from "effect/Option"
import * as Either from "effect/Either"

// 3. Schema imports (note the package path)
import * as S from "@effect/schema/Schema"  // ✅ CORRECT: @effect/schema
// NOT: import * as S from "effect/Schema"  // ❌ WRONG

// 4. Platform imports
import { HttpClient, HttpServer } from "@effect/platform"
import { NodeRuntime } from "@effect/platform-node"

// 5. Third-party imports
import * as fc from "fast-check"
```

**Critical Import Path Notes:**

- Schema comes from `@effect/schema/Schema`, NOT `effect/Schema`
- Platform utilities come from `@effect/platform` packages
- Runtime implementations are platform-specific (`@effect/platform-node`, `@effect/platform-bun`)

#### When to Use Descriptive Names

Use descriptive names instead of single-character aliases when:

1. **Multiple similar modules are imported** - Avoid confusion between `A` (Array) and `A` (different module)
2. **Code review requirements** - Team standards may prefer explicit names
3. **Learning codebases** - Descriptive names help newcomers
4. **Public APIs** - Examples in documentation should be clear

```typescript
// In documentation or public examples
import { Array as Arr, Option as Opt } from "effect"

// The code becomes more readable for newcomers
const result = pipe(
  Arr.filter(items, isActive),
  Arr.map(item => item.name),
  Opt.fromNullable
)
```

#### Consistency Guidelines

**Within a file:** Be consistent with your choice of aliases:

```typescript
// ✅ GOOD: Consistent usage
import * as A from "effect/Array"
const filtered = A.filter(items, predicate)
const mapped = A.map(filtered, transform)

// ❌ BAD: Mixing styles
import * as A from "effect/Array"
import * as Array from "effect/Array"  // Confusing!
const filtered = A.filter(items, predicate)
const mapped = Array.map(filtered, transform)
```

**Across a project:** Establish team conventions and document them:

```typescript
// Project-wide convention (example)
// - Use single-letter for: Schema (S), Option (O), Either (E)
// - Use descriptive for: Array (Arr), Function (Fn)
// - Always spell out: Effect, Layer, Context, Data
```

### 2.3 Critical Syntax Rules

#### FORBIDDEN: try-catch in Effect.gen

**NEVER use `try-catch` blocks inside `Effect.gen` generators!**

**Why this is forbidden:**

1. Effect generators handle errors through the Effect type system, not JavaScript exceptions
2. JavaScript try-catch only catches synchronous exceptions, not Effect's typed errors
3. Using try-catch breaks Effect's error channel and type safety
4. The catch block will never be reached for Effect failures
5. It prevents proper error propagation and interruption handling

**❌ WRONG: try-catch in Effect.gen**

```typescript
// ❌ ABSOLUTELY FORBIDDEN
Effect.gen(function* () {
  try {
    const result = yield* someEffect  // This doesn't work!
    return result
  } catch (error) {
    // ❌ This will NEVER be reached for Effect errors
    console.error("Caught error:", error)
    return defaultValue
  }
})
```

**✅ CORRECT: Use Effect's Error Handling**

```typescript
// ✅ Pattern 1: Use Effect.result for explicit handling
Effect.gen(function* () {
  const result = yield* Effect.result(someEffect)
  
  if (result._tag === "Failure") {
    // Handle error case
    console.error("Operation failed:", result.cause)
    return defaultValue
  }
  
  return result.value
})

// ✅ Pattern 2: Use Effect.either
Effect.gen(function* () {
  const result = yield* Effect.either(someEffect)
  
  if (result._tag === "Left") {
    // Handle error
    return defaultValue
  }
  
  return result.right
})

// ✅ Pattern 3: Use Effect.try for synchronous code that may throw
Effect.gen(function* () {
  const parsed = yield* Effect.try({
    try: () => JSON.parse(jsonString),
    catch: (error) => new JsonParseError({ cause: error })
  })
  
  return parsed
})

// ✅ Pattern 4: Use Effect.tryPromise for async code
Effect.gen(function* () {
  const data = yield* Effect.tryPromise({
    try: () => fetch(url).then(r => r.json()),
    catch: (error) => new NetworkError({ cause: error })
  })
  
  return data
})

// ✅ Pattern 5: Use .pipe with catchTag
Effect.gen(function* () {
  const result = yield* someEffect
  return result
}).pipe(
  Effect.catchTag("SpecificError", (error) =>
    Effect.succeed(defaultValue)
  )
)
```

#### FORBIDDEN: Type Assertions

**NEVER use `as any`, `as never`, or `as unknown` type assertions!**

**Why this is forbidden:**

1. Type assertions destroy TypeScript's type safety
2. They hide real type errors that should be fixed
3. They create a false sense of security
4. They lead to runtime errors that could have been caught at compile time
5. They make code unmaintainable and error-prone

**❌ WRONG: Type Assertions**

```typescript
// ❌ ABSOLUTELY FORBIDDEN - Never use these
const value = something as any
const value = something as never  
const value = something as unknown

// ❌ Also forbidden - casting to bypass type checking
const result = (apiResponse as User).name
```

**✅ CORRECT: Fix the Type Issue**

```typescript
// ✅ Option 1: Use proper generic type parameters
function processData<T>(data: T): Effect.Effect<T> {
  return Effect.succeed(data)
}

// ✅ Option 2: Import correct types
import type { User } from "./types"
const user: User = yield* getUser()

// ✅ Option 3: Use Effect constructors
const data = yield* Effect.tryPromise({
  try: () => fetchData(),
  catch: (error) => new FetchError({ cause: error })
})

// ✅ Option 4: Use Schema for validation
import * as S from "@effect/schema/Schema"
const User = S.Struct({
  id: S.String,
  name: S.String
})
const validated = yield* S.decodeUnknown(User)(unknownData)

// ✅ Option 5: Use satisfies for object conformance
const config = {
  host: "localhost",
  port: 3000
} satisfies Config  // Ensures type conformance without casting

// ✅ Option 6: Adjust function signatures
// Instead of casting return values, fix the function signature
function processUser(user: User): Effect.Effect<ProcessedUser> {
  // Return the correct type
  return Effect.succeed({
    id: user.id,
    displayName: user.name.toUpperCase()
  })
}
```

**When TypeScript complains about types:**

1. **Check your imports** - Are you importing the right types?
2. **Check generic parameters** - Do your functions have correct type parameters?
3. **Use Schema validation** - For unknown data, validate it properly
4. **Fix the function signature** - If the return type is wrong, fix the function
5. **Use satisfies** - To ensure object conformance without losing type inference

#### MANDATORY: return yield* Pattern

**ALWAYS use `return yield*` when yielding terminal effects!**

**Why this is mandatory:**

1. Makes it explicit that the generator function terminates at that point
2. Enables correct TypeScript type narrowing
3. Prevents unreachable code warnings
4. Makes control flow clear to readers
5. Follows Effect-TS conventions

**Terminal Effects (requiring `return yield*`):**

- `Effect.fail()` - Returns an error
- `Effect.die()` - Dies with a defect
- `Effect.interrupt` - Interrupts the fiber
- `Effect.failCause()` - Fails with a cause
- Any other Effect that represents termination

**✅ CORRECT: return yield* Pattern**

```typescript
Effect.gen(function* () {
  // Check condition
  if (someErrorCondition) {
    // ✅ CORRECT: Use return yield* for errors
    return yield* Effect.fail(new ValidationError({ field: "email" }))
  }
  
  // Check another condition
  if (someFatalCondition) {
    // ✅ CORRECT: Use return yield* for defects
    return yield* Effect.die(new Error("Unrecoverable state"))
  }
  
  // Check interruption
  if (shouldInterrupt) {
    // ✅ CORRECT: Use return yield* for interrupts
    return yield* Effect.interrupt
  }
  
  // TypeScript knows the conditions above are false here
  const result = yield* someOtherEffect
  return result
})
```

**❌ WRONG: Missing return Keyword**

```typescript
Effect.gen(function* () {
  if (someErrorCondition) {
    // ❌ WRONG: Missing return keyword
    yield* Effect.fail(new ValidationError({ field: "email" }))
    // Unreachable code! TypeScript can't infer termination
  }
  
  // This line is incorrectly considered reachable
  const result = yield* someOtherEffect
  return result
})
```

**Benefits of return yield*:**

```typescript
Effect.gen(function* () {
  const user = yield* getUser(id)
  
  if (!user.isActive) {
    // With return yield*, TypeScript knows this terminates
    return yield* Effect.fail(new InactiveUserError())
  }
  
  // TypeScript knows user.isActive is true here
  // Without return yield*, this wouldn't be guaranteed
  return user.activate()  // Type-safe operation
})
```

### 2.4 TypeScript Conventions

#### const Over function Keyword

**Use `const` with arrow functions instead of the `function` keyword:**

```typescript
// ✅ PREFERRED: const with arrow function
const myFunction = (x: number, y: number): number => {
  return x + y
}

// ✅ Also acceptable: const with function expression
const myFunction = function(x: number, y: number): number {
  return x + y
}

// ❌ AVOID: function keyword
function myFunction(x: number, y: number): number {
  return x + y
}
```

**Rationale:**
- Consistent with functional programming style
- Arrow functions have lexical `this` binding
- Prevents accidental `this` context issues
- More concise for simple functions
- Aligns with Effect-TS patterns

**Exception:** Use `function*` for generator functions (required syntax):

```typescript
// ✅ Generator functions require function* syntax
Effect.gen(function* () {
  const result = yield* someEffect
  return result
})
```

#### undefined vs null

**Always use `undefined`. Never use `null`.**

```typescript
// ✅ CORRECT: Use undefined
const findUser = (id: string): User | undefined => {
  return users.find(u => u.id === id)
}

// ✅ Use Option for explicit absence
import * as O from "effect/Option"
const findUser = (id: string): O.Option<User> => {
  return O.fromNullable(users.find(u => u.id === id))
}

// ❌ WRONG: Don't use null
const findUser = (id: string): User | null => {
  return users.find(u => u.id === id) || null
}
```

**Rationale:**
- JavaScript has both `null` and `undefined`, which is redundant
- `undefined` is the default value for uninitialized variables
- Optional parameters automatically default to `undefined`
- Effect-TS Option type works naturally with `undefined`
- Reduces cognitive load by having one "absence" value

**Type signatures:**

```typescript
// ✅ CORRECT: Use undefined or Option
interface User {
  id: string
  name: string
  email: string
  phone?: string  // Optional, defaults to undefined
}

// ❌ WRONG: Don't use null in type signatures
interface User {
  id: string
  name: string
  email: string
  phone: string | null
}
```

#### Equality Checks

**Use `===` and `!==` for primitive type comparisons:**

```typescript
// ✅ CORRECT: Use strict equality for primitives
if (status === "active") { }
if (count !== 0) { }
if (name === user.name) { }

// ❌ AVOID: Loose equality
if (status == "active") { }
if (count != 0) { }
```

**For objects, use Effect's Equal utility:**

```typescript
import { Equal } from "effect"

// ✅ CORRECT: Use Equal for deep equality
const user1 = { id: "123", name: "John" }
const user2 = { id: "123", name: "John" }

if (Equal.equals(user1, user2)) {
  // Objects are deeply equal
}

// ❌ WRONG: Reference comparison for objects
if (user1 === user2) {
  // This compares references, not values!
  // Always false for different object instances
}
```

**Understanding JavaScript equality:**

```typescript
// Primitives: === compares values
const a = 5
const b = 5
console.log(a === b)  // true

const str1 = "hello"
const str2 = "hello"
console.log(str1 === str2)  // true

// Objects: === compares references
const obj1 = { x: 1 }
const obj2 = { x: 1 }
console.log(obj1 === obj2)  // false (different references)

const obj3 = obj1
console.log(obj1 === obj3)  // true (same reference)

// ✅ For value comparison, use Equal
console.log(Equal.equals(obj1, obj2))  // true (same values)
```

**Pattern for equality in Effect:**

```typescript
import { Equal, Data } from "effect"

// Define data with automatic Equal implementation
class User extends Data.Class<{
  id: string
  name: string
  email: string
}> {}

const user1 = new User({ id: "1", name: "John", email: "john@example.com" })
const user2 = new User({ id: "1", name: "John", email: "john@example.com" })

// Automatic deep equality
if (Equal.equals(user1, user2)) {
  // true - values are equal
}

// Can also use in Sets and Maps
const userSet = new Set([user1, user2])
console.log(userSet.size)  // 1 (deduplicated based on equality)
```

**Array and Collection Equality:**

```typescript
import { Equal, Array as A } from "effect"

// ✅ CORRECT: Deep equality for arrays
const arr1 = [1, 2, 3]
const arr2 = [1, 2, 3]

if (Equal.equals(arr1, arr2)) {
  // true - arrays have same values
}

// ❌ WRONG: Reference comparison
if (arr1 === arr2) {
  // false - different array instances
}

// ✅ For complex objects in arrays
const users1 = [
  { id: "1", name: "John" },
  { id: "2", name: "Jane" }
]
const users2 = [
  { id: "1", name: "John" },
  { id: "2", name: "Jane" }
]

if (Equal.equals(users1, users2)) {
  // true - deep equality check
}
```

**Best Practices:**

1. **Primitives** - Use `===` and `!==` for numbers, strings, booleans
2. **Objects** - Use `Equal.equals()` for value comparison
3. **Arrays** - Use `Equal.equals()` for deep comparison
4. **Sets/Maps** - Effect's Data structures use Equal automatically
5. **Reference checks** - Use `===` only when you specifically need reference equality
